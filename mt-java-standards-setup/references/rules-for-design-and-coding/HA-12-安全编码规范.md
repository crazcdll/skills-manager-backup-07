# 安全编码规范（认证与越权）

## 一、说明

本规范是**认证与越权防护的唯一权威规范（SSOT）**。本文件仅覆盖这两个高优先级话题，其他安全主题参见：

| 安全主题 | 规范文件 |
|----------|---------|
| 注入类（OS命令/XXE/SQL注入/Cookie/CSRF/重定向） | `SEC-01-注入安全规范.md` |
| 数据保护（XSS/脱敏/Token传递/加解密/反序列化） | `SEC-02-数据保护规范.md` |
| 访问控制（文件操作安全/SSRF） | `SEC-03-访问控制与网络安全规范.md` |
| SQL 注入参数绑定 | `DB-01` ORM002 |

## 二、规则内容

以下示例仅用于说明规则边界与意图，不代表唯一实现方式；实际生成或审查代码时，应优先复用项目现有框架、工具类、SDK 与命名，并以是否满足规则约束为判断标准。

### HA-SEC001 [推荐] 接口建议配置认证

所有对外接口建议配置认证拦截器或注解，删除或绕过认证等同于接口裸奔。

**说明**：
- 新增接口建议确认已挂载认证拦截器（如 `@RequiresPermission`、`@PreAuthorize`、Shiro 注解）
- 内部服务间调用也建议配置服务间认证（mTLS/SOAMesh 或内部 JWT）
- 删除认证注解 / 绕过认证过滤器在 CR 中建议标记为推荐级别问题

##### good case:

```java
// 对外接口：权限注解
@GetMapping("/api/user/{id}")
@RequiresPermission("user:read")
public Result<UserDTO> getUser(@PathVariable Long id) {
    return userService.getUserById(id);
}

// 内部服务间：内部认证
@InternalService  // 或 @SsoAccess
public OrderResult createOrder(OrderRequest request) {
    return orderService.createOrder(request);
}
```

##### bad case:

```java
// 新增接口无任何认证 — 任何人可调用！
@PostMapping("/api/order")
public Result<OrderDTO> createOrder(@RequestBody OrderDTO dto) {
    return orderService.createOrder(dto);
}

// 绕过认证
@SkipAuthentication
@Delete("/api/user/{id}")
public void deleteUser(@PathVariable Long id) { /* 危险！ */ }
```

### HA-SEC002 [推荐] 建议防止越权访问

水平越权和垂直越权建议在业务逻辑中校验，不建议仅依赖前端隐藏按钮。

**说明**：

- **水平越权**：用户 A 不建议访问用户 B 的数据。查询条件建议包含当前用户标识（userId / tenantId）
- **垂直越权**：普通用户不建议访问管理员接口。权限校验建议在后端独立执行
- 越权校验建议封装为通用工具方法（如 `SecurityUtils.checkOwnership(resource, currentUser)`）

##### good case:

```java
// 水平越权防护：查询条件包含当前用户
public Order getOrder(Long orderId) {
    Long currentUserId = SecurityContext.getCurrentUserId();
    Order order = orderMapper.selectById(orderId);
    if (order == null || !order.getUserId().equals(currentUserId)) {
        throw new ForbiddenException("无权访问此订单");
    }
    return order;
}

// 垂直越权防护：管理员接口后端强制校验角色
@Delete("/api/admin/config/{configId}")
@RequiresRole("ADMIN")  // 后端强制校验角色，不依赖前端隐藏
public void deleteConfig(@PathVariable Long configId) { /* ... */ }
```

##### bad case:

```java
// 仅根据 orderId 查询 — 任何人可查任何订单！
public Order getOrder(Long orderId) {
    return orderMapper.selectById(orderId); // 无 userId 校验
}

// 仅靠前端隐藏按钮 — 攻击者可直接调 API
@PostMapping("/admin/reset-data")
public void resetData() { /* 无任何权限检查 */ }
```

## 三、实践建议

1. 所有对外接口建议有认证
2. 业务逻辑中建议包含越权校验
3. 认证和越权校验不依赖于前端控制
4. CR 中发现无认证或无越权校验建议标记为推荐级别问题

## 四、规范执行要点

### 不建议做法
- ✗ 不建议接口不配置认证就上线
- ✗ 不建议仅靠前端隐藏按钮实现权限控制
- ✗ 不建议在查询条件中缺少当前用户标识

### 代码审查检查点
- [ ] 新增接口是否配置了认证
- [ ] 是否存在仅靠前端隐藏的权限控制
- [ ] 数据查询是否包含当前用户标识（水平越权）
- [ ] 管理操作是否有额外的角色校验（垂直越权）
- [ ] CR 中是否将无认证/无越权问题标记为推荐级别
