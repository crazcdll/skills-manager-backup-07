## 一、前端问题修复

**适用场景**：根因定位到前端代码（JS 异常、逻辑错误、组件问题等），确认是前端代码 Bug。

### 前置：检查 code-cli 环境

在执行任何 Git / PR 操作前，先验证 `code-cli` 已安装并已登录：

**Step 0.1 检查安装**
```bash
code-cli --version
```
若命令不存在，提示用户安装：
```bash
npm install -g @ee/code-cli --registry=aHR0cDovL3IubnBtLnNhbmt1YWkuY29t
```

**Step 0.2 检查登录状态**
```bash
code-cli auth status
```
若未登录，自动执行：
```bash
code-cli auth login
```
登录成功后继续；若失败则停止并提示用户手动登录。

---

### 修复步骤

#### Step 1. 定位代码

根据第四步排查结论中的堆栈或日志，确认：
- 仓库地址（git remote URL）
- 出错文件路径 + 行号
- 问题代码逻辑

确保当前工作目录已切换到对应仓库，并拉取最新代码：
```bash
git fetch origin
git checkout <默认分支，通常为 master 或 main>
git pull origin <默认分支>
```

#### Step 2. 创建 feature 修复分支

> **⚠️ 严禁直接在默认分支上修改代码。** 必须创建独立的 feature 分支。

**2.1 获取默认分支**
```bash
code-cli repo branch default --json
```

**2.2 创建并切换到 feature 分支**

分支命名规范：`hotfix/stability-<简短描述>-<YYYYMMDD>`，例如：
```bash
git checkout -b hotfix/stability-fix-null-check-20260429
```

> 若问题有关联 ONES 工作项，可使用 `feature/PRJ-<issue_id>/<简短描述>` 格式。

#### Step 3. 分析根因，编写修复代码

- 理解问题代码的逻辑，确认修复方案
- 在新分支上修改对应文件，确保：
  - 修复范围最小化，不引入新问题
  - 保持代码风格与原有代码一致
  - 如有必要，补充单元测试或防御性判断

#### Step 4. 提交修复代码

```bash
git add <修改的文件>
git commit -m "fix: <简短描述问题和修复方式>"
```

提交信息建议格式：`fix: [业务线] <问题描述> - <修复方式>`，例如：
```
fix: [meishi] 修复下单页空指针异常 - 增加 userInfo 判空保护
```

#### Step 5. 推送分支到远程

```bash
git push origin <feature分支名>
```

#### Step 6. 创建 PR

**6.1 检查是否已有同分支 PR**
```bash
code-cli pr list -H <feature分支名> -s open --json
```
若已存在 PR，直接使用已有 PR，跳到 Step 7。

**6.2 获取目标分支和候选评审人**
```bash
# 获取默认目标分支
code-cli repo branch default --json

# 获取候选评审人
code-cli repo reviewers -t <目标分支> --json
```

**6.3 检查仓库是否要求绑定 ONES 工作项**
```bash
code-cli repo settings --json
```
若 `requireIssueAssociated` 为 `true`，需先在 MCode 分支管理页面绑定 ONES 工作项，再继续。

**6.4 创建 PR**
```bash
code-cli pr create \
  -t "fix: [稳定性修复] <问题简述>" \
  -b "<详细描述：问题现象、根因、修复方案>" \
  -B <目标分支> \
  -r <代码Owner mis_id> \
  --json
```

PR 描述模板：
```
## 问题背景
<告警/TT工单/客诉描述>

## 根因分析
<第四步排查结论>

## 修复方案
<具体修改内容>

## 影响范围
<修改的文件/模块，是否有风险>

## 验证方式
<如何验证修复有效>
```

1. **整理证据**：收集 traceId、错误码、错误信息、影响时间段

## 三、变更引入问题

**适用场景**：根因为某次发布变更引入（Diva / Horn / MCM 等）

### 处理步骤

1. **确认止损状态**：检查第三步的止损是否已完成，未完成则立即执行
2. **通知发布人**：告知变更引入了问题，需要修复后重新发布
3. **跟进修复**：等待发布人修复代码并重新发布，观察指标恢复

输出前，**必须**先执行以下命令，获取结束时间：

```bash
endTime=$(date "+%Y-%m-%d %H:%M:%S") && echo $endTime
```

## 四、无法定位根因

**适用场景**：日志和变更均无明确结论

### 处理步骤

1. **扩大排查范围**：延长时间窗口、扩大业务线范围
2. **上报升级**：若影响核心链路，上报 P1/P0，启动故障处置 SOP
3. **持续观察**：记录当前状态，等待更多信息

### 输出信息

输出前，**必须**先执行以下命令，获取结束时间：

```bash
endTime=$(date "+%Y-%m-%d %H:%M:%S") && echo $endTime
```
