## 检查工作流程

### 步骤 0: 清理工作区
检查项目根目录下 `.spec/` 目录中是否有过时文件。创建必要目录：
```bash
mkdir -p .spec/file .spec/result
```

如有上次执行残留的 `tabelOhPackage-dep.md`、`tabelCommonPackage-dep.md`，先删除或覆盖。

### 步骤 1: 创建鸿蒙依赖信息对照表

提取 `oh-package.json` 中的依赖信息，按 `dependencies`、`devDependencies`、`resolutions` 字段分别创建表格（表格名称：tabelOhPackage-dep），整理到 `.spec/file/tabelOhPackage-dep.md` 中。

**表格列定义：**
- 依赖名称
- 当前版本（`oh-package.json` 中实际使用的版本）
- 鸿蒙支持最新版本（严格与 k-hub 知识库中一致，含 `^` 等符号）
- 是否支持 Android/iOS（是✅ / 否❌）

**查询与填写规则：**
- 以 k-hub 知识库中的依赖名称做**完全匹配**查询，严禁模糊匹配。
- 若文档中存在该依赖，取「版本号」列的值作为「鸿蒙支持最新版本」。
- 若文档说明该版本支持三个系统，则「是否支持 Android/iOS」填「是✅」，否则填「否❌」。
- 若文档中不存在该依赖，「鸿蒙支持最新版本」留空，并在步骤 3 中提示用户重点关注。

<example>
| 依赖名称 | 当前版本 | 鸿蒙支持最新版本 | 是否支持 Android/iOS |
|---|---|---|---|
| @max/meituan-uni-knb | 2.0.13 | ^2.0.14 | 是✅ |
| @mrn/mrn-cli | 4.0.0-beta.26 | 4.0.1 | 否❌ |
</example>

### 步骤 2: 创建通用依赖信息对照表

提取 `package.json` 中的依赖信息，按 `dependencies`、`devDependencies`、`resolutions` 字段分别创建表格（表格名称：tabelCommonPackage-dep），整理到 `.spec/file/tabelCommonPackage-dep.md` 中。

**表格列定义：**
- 依赖名称
- 当前版本（`package.json` 中当前使用的版本）
- 三个系统都兼容的版本（来自 k-hub 知识库）

**版本取值规则：**
- 关联步骤 1 中生成的鸿蒙依赖表，查找同名依赖。
- 如果鸿蒙依赖表中「是否支持 Android/iOS」为「是」，则将鸿蒙依赖表中的「鸿蒙支持最新版本」填入本表的「三个系统都兼容的版本」列。
- **冲突解决**：当鸿蒙依赖表中存在多个同名依赖时，以 `resolutions` 字段下的内容为准。
- 其他情况（不支持或不匹配）不填值，填「-」。
- 如果知识库记录的为模糊版本（如 `^2.0.14`），按原样记录。
- 若文档中三端兼容版本为空，提示用户重点关注。
- `@max/meituan-uni-xx` 各包可用的最新版本不同，不要混淆。

<example>
| 依赖名称 | 当前版本 | 三个系统都兼容的版本 |
|---|---|---|
| @max/meituan-uni-knb | 2.0.13 | ^2.0.14 |
| @mrn/mrn-cli | 3.0.8 | - |
</example>

### 步骤 3: 汇总特殊情况与建议

整理在 k-hub 知识库中未收录的依赖列表，提示用户重点关注兼容性问题。确保所有依赖均已完成比对。

输出格式示例：
```
## ⚠️ 未在知识库中收录的依赖（需用户人工核查）
- `@some/unknown-package`（oh-package.json dependencies）
- `@another/package`（package.json devDependencies）
```
</sop>

<boundary>
## 工作边界

**工作范围：**
- 读取并解析 `package.json` 和 `oh-package.json` 文件内容。
- 依据 k-hub 知识库进行依赖版本查询和匹配。
- 生成结构化的依赖对照表格，写入 `.spec/file/` 目录。

**不应该做的事情：**
- 不进行模糊匹配，必须严格按依赖名称完全匹配。
- 不随意猜测或修改未在 k-hub 知识库中列出的依赖版本。
- 不执行实际的依赖安装或构建命令。
- 不使用 Citadel、内网浏览器或其它非 k-hub 渠道作为版本来源。
- 对知识库未收录的依赖不做主观改版本，仅提示用户。
</boundary>

<constraints>
## 执行约束

**执行方式：**
- 必须严格按照字段分类（dependencies、devDependencies、resolutions）生成表格。
- 查询依赖版本时必须精准匹配，禁止模糊搜索。
- 遇到同名依赖冲突时，严格遵循「resolutions 字段优先」原则。

**输出质量要求：**
- 表格格式清晰，列名与步骤定义保持一致。
- 对于未在文档中记录的依赖，必须在最后明确列出提示。

**沟通风格：**
- 使用结构化的 Markdown 表格展示结果。
- 保持客观、精准的描述，不添加无关建议。
</constraints>
