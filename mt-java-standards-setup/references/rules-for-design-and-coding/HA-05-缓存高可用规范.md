# 缓存高可用规范

## 一、说明

本规范定义了缓存操作的高可用标准，涵盖缓存一致性、容量治理、缓存防护和序列化安全四个领域。缓存是高并发系统的核心组件，缓存故障（穿透、击穿、雪崩、BigKey）可能直接导致数据库被打崩。

## 二、规则内容

### HA-C001 [推荐] 缓存一致性建议使用 Cache Aside 模式

缓存与数据库的一致性建议使用 Cache Aside 标准模式：读操作先读缓存、miss 后读 DB 并回填；写操作先更新 DB、再删除缓存。

**说明**：
- 不建议"先删缓存再更新 DB"（会导致并发读写时缓存脏数据）
- 高一致性要求场景可补充延迟双删（更新 DB 后延迟 500ms~1s 再次删除缓存）
- 所有缓存建议设置 TTL，不建议永不过期的缓存
- TTL 建议加随机抖动（如 TTL = baseTime + random(0, 60s)），防止缓存雪崩

### HA-C002 [推荐] BigKey 和 HotKey 建议治理

缓存 Key 的大小和访问频率建议控制在安全阈值内。

**说明**：
- Squirrel（Redis）：String ≤512KB、Hash/List/Set/ZSet 元素数 ≤5000
- Cellar（Tair）：Value ≤10KB
- 超出阈值的 Key 建议拆分（如大 Hash 拆分为多个小 Hash）
- Pipeline 单次命令数 ≤512，multiGet 单次 Key 数 ≤1024
- 不建议对大集合执行 O(N) 全量操作（如 `HGETALL`、`SMEMBERS`）

### HA-C003 [推荐] 缓存防护三件套

建议针对缓存穿透、击穿、雪崩分别设置防护措施。

**说明**：
- **穿透防护**：对于 DB 中也不存在的数据，缓存空值（短 TTL）或使用布隆过滤器
- **击穿防护**：热点 Key 过期时，使用互斥锁（`SETNX` + 超时）+ 双重检查，防止大量请求同时打到 DB
- **雪崩防护**：TTL 加随机抖动，避免大批 Key 同时过期
- 缓存不可用时建议有降级策略（如直接读 DB + 限流），缓存异常不建议阻断主流程

### HA-C004 [推荐] 序列化建议保证兼容性

缓存的序列化/反序列化建议保证版本兼容，防止发布时缓存数据无法反序列化。

**说明**：
- 不建议修改缓存对象的类全限定名（会导致反序列化失败）
- StoreKey 建议使用 `StoreKey(category, template)` 方式构建，不建议字符串拼接
- 不建议使用 Squirrel 的 pubsub 功能
- 新增字段建议有默认值，删除字段建议确认缓存已过期或已清理

## 三、示例

以下示例仅用于说明规则边界与意图，不代表唯一实现方式；实际生成或审查代码时，应优先复用项目现有框架、工具类、SDK 与命名，并以是否满足规则约束为判断标准。

### HA-C001 Cache Aside 示例

#### good case:

```java
// 读操作：先缓存，miss 后读 DB 回填
public User getUser(Long userId) {
    String key = "user:" + userId;
    User user = cache.get(key);
    if (user != null) return user;

    user = userMapper.selectById(userId);
    if (user != null) {
        cache.set(key, user, 300 + ThreadLocalRandom.current().nextInt(60)); // TTL 抖动
    }
    return user;
}

// 写操作：先更新 DB，再删缓存
@Transactional
public void updateUser(User user) {
    userMapper.update(user);
    cache.delete("user:" + user.getId());
}
```

#### bad case:

```java
// 先删缓存再更新 DB — 并发场景下会导致脏数据
public void updateUser(User user) {
    cache.delete("user:" + user.getId()); // 此时另一个读请求可能回填旧数据
    userMapper.update(user);
}

// 永不过期的缓存
cache.set("user:" + userId, user); // 无 TTL
```

### HA-C003 穿透防护示例

#### good case:

```java
// 空值缓存防护穿透
public User getUser(Long userId) {
    String key = "user:" + userId;
    ValueWrapper wrapper = cache.get(key);
    if (wrapper != null) {
        return wrapper.getValue(); // 可能是 null（空值缓存）
    }

    User user = userMapper.selectById(userId);
    if (user == null) {
        cache.set(key, NULL_PLACEHOLDER, 60); // 空值缓存，短 TTL
    } else {
        cache.set(key, user, 300 + ThreadLocalRandom.current().nextInt(60));
    }
    return user;
}
```

## 四、规范执行要点

- ✗ 不建议先删缓存再更新 DB
- ✗ 不建议缓存不设置 TTL
- ✗ 不建议对大集合执行 O(N) 全量操作
- ✗ 不建议 Pipeline 超过 512 个命令
- ✗ 不建议修改缓存对象的类全限定名
- ✗ 不建议使用 Squirrel pubsub
- ✗ 不建议缓存异常阻断主流程
