## 大象群聊推送模板（Step 8）

```
【AI-CR】{conclusion} | {org}/{repo} PR #{id}

功能：{title}
提交人：{authorName}（{submitter_mis}）
触发人：{triggerName}（{triggerMis}）
涉及文件：{fileCount} 个（+{additions} / -{deletions}）

发现：P0: {p0} | P1: {p1} | P2: {p2} | P3: {p3}

{top_issues_text}
{layer2_warning}
📄 详细文档：{kmUrl}
🔗 PR 链接：{prUrl}
```

> 说明：
> - `{triggerName}（{triggerMis}）`：触发本次 CR 的人（通常是 code reviewer / 木子），格式与提交人一致：姓名（mis）。triggerMis 从当前 session 的操作者 mis 获取，triggerName 通过 `code_cli.py user-info {triggerMis}` 或同名映射获取
> - `{top_issues_text}`：若有 P0/P1，逐条列出（每条一行，格式 `• P1-01 问题标题`）；全通过则写 `✨ 未发现 P0/P1 问题`
> - 多仓库联合 CR：每个 PR 各列一行链接，结论取最高级别（有 P0 就是 P0）
> - 消息纯文本，不 @ 任何人（群广播模式）

## 去重规则

**行内评论（Step 7A）**：发布前必须检查 PR 中该文件+行号是否已有相同问题的评论（含人工和 AI 评论）。同一文件 + 同一行号 + 相同问题类型（同一 ruleId 或同一异常类型）→ **跳过不重复写入**。

**全局评论（Step 7B）**：P2/P3 若已在行内评论中标注同一文件同一行同一问题，**不在全局评论中重复列出**。P0/P1 在全局评论中列出摘要（问题标题+文件+行号），与行内评论形成互相引用，但不重复完整描述。

## P1 报出门槛（内部校验，不输出到文档）

每条疑似 P1 在内部必须满足：
1. **diff 中有明确代码证据**（具体行号 + 代码片段），不是推测
2. **能说清线上影响场景**：什么请求/什么数据/什么时机会触发，禁止"理论上可能"
3. **排除已有保护**：确认调用链上没有 try-catch、降级、兜底等已有防护

**不满足的直接归为 P2/P3 或不报，不在文档中提及判定过程。** 以下场景禁止报 P1：
- "超时时间可能不够" — 无数据支撑的猜测 → 归为 P2/P3
- "没有 failover" — 直连测试环境等非核心链路 → 归为 P2/P3
- "没有重试" — 用户主动触发的同步操作 → 归为 P2/P3
- "没有事务" — 跨 RPC + 乐观锁 + 逐步 catch 有意设计 → 不报
- "catch(Exception) 范围过宽" — 已有 log.error + Cat 上报 → 归为 P2

P1 输出格式同 P0（所有字段必须有实质内容）。

**软警告模板（31-50 个触发器）：**

```
⚠️ PR 规模提示：本次变更产生 {N} 个触发器，Layer 2 已全部执行但分析质量可能受影响。建议拆分 PR：
• 按功能模块拆分：每个特性/需求独立一个 PR
• 按架构层拆分：DTO/接口层 + 业务逻辑层 + 配置/基础设施层分开提交
• 按变更类型拆分：新功能 + 重构 + 配置变更分开提交
```

**硬截断模板（>50 个触发器）：**

```
🔴 PR 规模超限：本次变更产生 {N} 个触发器，Layer 2 已截断至前 30 个（按 P0>P1>P2 优先级），变更影响分析覆盖不完整。强烈建议拆分 PR：
• 按功能模块拆分：每个特性/需求独立一个 PR
• 按架构层拆分：DTO/接口层 + 业务逻辑层 + 配置/基础设施层分开提交
• 按变更类型拆分：新功能 + 重构 + 配置变更分开提交
• 未覆盖的 {N-30} 个触发器可能涉及潜在兼容性问题，建议拆分后重新 Review
```
