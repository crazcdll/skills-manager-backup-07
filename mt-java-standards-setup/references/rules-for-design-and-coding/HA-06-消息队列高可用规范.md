# 消息队列高可用规范

## 一、说明

本规范定义了消息队列（Mafka）操作的高可用标准，涵盖生产端可靠发送、消费端安全处理和积压处理三个领域。消息积压和丢失是常见的线上故障类型，正确使用 MQ 是保证系统最终一致性的关键。

## 二、规则内容

### HA-M001 [推荐] 生产端建议检查发送结果

每次消息发送后建议检查 `SendResult`，发送失败时建议有补偿机制（重试或本地消息表）。

**说明**：
- 不建议 fire-and-forget（发了就不管），建议检查发送结果
- 消息体建议使用 JSON 格式，便于排查和跨语言消费
- 消息 Key 建议包含业务含义（如 orderId），用于消息追踪和去重
- 需要和 DB 操作保证原子性时，使用事务消息或本地消息表模式

### HA-M002 [推荐] 消费端建议幂等且全量 catch

消费逻辑建议保证幂等性（推荐），消费方法建议全量 catch 异常。

**说明**：
- 幂等实现：通过消息 Key + Squirrel/DB 唯一约束实现去重
- 消费方法建议 `try-catch(Throwable)`，防止未知异常导致消费线程挂掉
- 消费失败应返回 `RECONSUME_LATER`（重新入队稍后重试），不建议返回 `CONSUME_FAILURE`（直接丢弃）
- 重试超过 3~5 次仍失败的消息应进入死信队列，人工介入处理
- 去重 TTL 建议大于重试窗口（建议 ≥7 天）

### HA-M004 [推荐] 积压建议有告警和处理策略

消费积压建议配置告警，并提供快速消化策略。

**说明**：
- 配置 Raptor 告警：积压超过阈值（如 1000 条）时告警
- 积压处理策略：增加消费者实例、提高消费并发度、紧急跳过非核心消息
- 不建议通过清空 topic 的方式处理积压

## 三、示例

以下示例仅用于说明规则边界与意图，不代表唯一实现方式；实际生成或审查代码时，应优先复用项目现有框架、工具类、SDK 与命名，并以是否满足规则约束为判断标准。

### HA-M001 生产端示例

#### good case:

```java
public void sendOrderMessage(Order order) {
    Message msg = new Message("order_topic", JSON.toJSONString(order));
    msg.setKey(String.valueOf(order.getId())); // 业务含义的 Key

    SendResult result = producer.send(msg);
    if (result == null || result.getSendStatus() != SendStatus.SEND_OK) {
        log.error("send message failed, orderId={}, result={}", order.getId(), result);
        // 补偿：写入本地消息表，定时任务重试
        localMessageService.save(msg);
    }
}
```

#### bad case:

```java
// fire-and-forget，不检查发送结果
producer.send(new Message("order_topic", JSON.toJSONString(order)));
```

### HA-M002 消费端示例

#### good case:

```java
@Override
public ConsumeConcurrentlyStatus consumeMessage(List<MessageExt> msgs, ConsumeConcurrentlyContext context) {
    for (MessageExt msg : msgs) {
        try {
            String key = msg.getKeys();
            // 幂等检查
            if (deduplicationService.isDuplicate(key)) {
                log.info("duplicate message, skip, key={}", key);
                continue;
            }
            // 业务处理
            processOrder(JSON.parseObject(msg.getBody(), Order.class));
            deduplicationService.markProcessed(key);
        } catch (Throwable e) {
            log.error("consume message failed, msgId={}", msg.getMsgId(), e);
            return ConsumeConcurrentlyStatus.RECONSUME_LATER; // 稍后重试
        }
    }
    return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
}
```

#### bad case:

```java
// 无幂等检查、无全量 catch、使用 CONSUME_FAILURE
@Override
public ConsumeConcurrentlyStatus consumeMessage(List<MessageExt> msgs, ConsumeConcurrentlyContext context) {
    for (MessageExt msg : msgs) {
        processOrder(JSON.parseObject(msg.getBody(), Order.class)); // 可能 NPE
    }
    return ConsumeConcurrentlyStatus.CONSUME_SUCCESS;
}
```

## 四、规范执行要点

### 不建议做法
- ✗ 不建议不检查消息发送结果
- ✗ 不建议消费逻辑不保证幂等
- ✗ 不建议使用 CONSUME_FAILURE（消息会被直接丢弃）
- ✗ 不建议消费方法不做全量 catch
- ✗ 不建议通过清空 topic 处理积压

### 代码审查检查点
- [ ] 消息发送后是否检查 SendResult
- [ ] 发送失败是否有补偿机制
- [ ] 消费逻辑是否保证幂等
- [ ] 消费方法是否全量 catch(Throwable)
- [ ] 消费失败是否返回 RECONSUME_LATER
- [ ] 是否配置了积压告警
