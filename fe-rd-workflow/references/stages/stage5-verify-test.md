# Stage 5：验证测试

## 阶段概述

> **目标**：对物料组件和页面协议产出的代码进行多维度验证，确保质量达标。
> **阻塞级别**：🟡 半阻塞 — P0 问题必须修复；P1/P2 可记录后延后。

---

## 输入

| 输入项 | 来源 | 说明 |
|--------|------|------|
| 代码产物 | Stage 4 输出 | 物料组件 + 协议文件 + 业务逻辑 |
| 需求分析文档 | Stage 3 输出 | 功能点和验收标准 |
| 技术方案 | Stage 3 输出 | 设计预期 |
| workflow-context | Stage 4 更新 | 物料组件和页面协议完成状态 |

---

## 过程

### Step 5.1：Code Review

**依赖 Skill（必选）**：载入 `fe-ai-review` skill，完成代码审查。缺失时暂停，提示用户安装（`mtskills i fe-ai-review`）。

**委托方式**：回忆并整理以下信息，以自然语言方式传达 `fe-ai-review` ：

- **审查对象**：`{base_branch}...{feature_branch}` 这段分支差异（从 Stage 3 技术方案 / 当前 git 状态提取）
- **背景信息**：技术方案文档、需求分析文档（路径或链接）
- 其它你认为有需要或有风险的背景信息，自行判断并提供



**阻断判定**（基于 `fe-ai-review` 报告中的「审查结论」字段）：

| 报告结论 | 后续行为 |
|---|---|
| ✅ 可合并 / ✅ 可合并（有优化建议） | 进入 Step 5.2，P2-P3 记入技术债 |
| ⚠️ 修复后可合并（含 P1，无 P0） | AskUserQuestion：修复后重跑 Step 5.1 / 书面确认风险后继续 |
| ❌ 不建议合并（含 P0） | 返回 Stage 4 定向修复 P0，回到 Step 5.1 重跑 |

> 若报告里出现 `Open Questions`，把每条作为澄清问题向用户确认，再决定是否进入 Step 5.2。

### Step 5.2：问题分级与处理

```yaml
问题分级标准:
  P0 (零容忍):
    - 编译/运行时报错
    - 核心功能不可用、白屏等严重后果
    - 数据丢失风险
    → 必须立即修复，阻塞合并

  P1 (高风险):
    - 非核心功能异常
    - 安全隐患
    - 可能影响用户体验（如性能）或代码质量劣化
    → 建议立即修复，可申请延后或说明依据

  P2 (建议优化):
    - 代码风格问题、注释缺失、可优化的写法
    → 记录到技术债，后续迭代处理

  P3 (低优/现代化建议):
    - 性能优化建议、现代化写法替换
    → 记录到技术债，不阻塞合并
```

### Step 5.3：生成验收清单

输出 `03-implementation-checklist.md`：

```markdown
# 实现验收清单

## 1. 静态检查结果
## 2. 功能验证结果
## 3. Code Review 结果
## 4. 问题清单（P0/P1/P2）
## 5. 遗留风险说明
## 6. 测试结论：通过 / 有条件通过 / 不通过
```

---

## 验证结论判定

| 结论 | 条件 | 后续动作 |
|------|------|----------|
| **通过** | 无 P0/P1 问题 | → 进入 Stage 6 |
| **有条件通过** | 有 P1 但无 P0 | → 用户确认后进入 Stage 6 |
| **不通过** | 存在 P0 问题 | → 返回 Stage 4 修复 |

---

## 异常处理

| 场景 | 处理方式 |
|------|----------|
| 无法启动本地服务 | 检查端口占用、依赖完整性 |
| Mock 数据不足 | 补充 mock 场景或使用真实环境 |
| 测试环境不可用 | 跳过集成测试，加强静态检查 |
