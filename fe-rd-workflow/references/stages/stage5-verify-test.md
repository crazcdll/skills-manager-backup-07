# Stage 5：验证测试

## 阶段概述

> **目标**：对物料组件和页面协议产出的代码进行多维度验证，确保质量达标。
> **阻塞级别**：🟡 半阻塞 — P0 问题必须修复；P1/P2 可记录后延后。

---

## 输入

| 输入项 | 来源 | 说明 |
|--------|------|------|
| 代码产物 | Stage 4 输出 | 物料组件 + 协议文件 + 业务逻辑 |
| 需求分析文档 | Stage 3 输出 | 功能点和验收标准 |
| 技术方案 | Stage 3 输出 | 设计预期 |
| workflow-context | Stage 4 更新 | 物料组件和页面协议完成状态 |

---

## 过程

### Step 5.1：Code Review

**依赖 Skill（必选）**：载入 `fe-ai-review` skill，完成代码审查。缺失时暂停，提示用户安装（`mtskills i fe-ai-review`）。

**委托方式**：回忆并整理以下信息，以自然语言方式传达 `fe-ai-review` ：

- **审查对象**：`{base_branch}...{feature_branch}` 这段分支差异（从 Stage 3 技术方案 / 当前 git 状态提取）
- **背景信息**：技术方案文档、需求分析文档（路径或链接）
- 其它你认为有需要或有风险的背景信息，自行判断并提供



**阻断判定**（基于 `fe-ai-review` 报告中的「审查结论」字段）：

| 报告结论 | 后续行为 |
|---|---|
| ✅ 可合并 / ✅ 可合并（有优化建议） | 进入 Step 5.2，P2-P3 留待 Step 5.3 记入技术债 |
| ⚠️ 修复后可合并（含 P1，无 P0） | AskUserQuestion：修复后重跑 Step 5.1 / 书面确认风险后继续 |
| ❌ 不建议合并（含 P0） | 返回 Stage 4 定向修复 P0，回到 Step 5.1 重跑 |

> 若报告里出现 `Open Questions`，把每条作为澄清问题向用户确认，再决定是否进入 Step 5.2。

### Step 5.2：Flow 用例自查

> **内循环约束：本步骤不执行任何自动化测试。** 端到端自动化测试属于外循环，由 `ai-auto-ui-test` 在研发流程之外独立发起。本步骤只做人工/Agent 对照自查。

**输入**：`.duo/{demand_description}/ui-test/flows/`（Stage 3 Step 3.4 产出，Stage 4 已作为 TDD 驱动使用）

**跳过条件**（满足任一即可跳过，需在清单中记录原因）：

- Stage 3 Step 3.4 被跳过，无 Flow 用例
- 本次变更不涉及页面可视层

**自查方式**：逐条对照 Flow 用例的「校验」项确认实现情况，按三态分类区别处理：

| 三态分类 | 自查方式 |
|---|---|
| `deterministic` | 阅读代码 / 本地渲染确认校验点已实现 |
| `data-dependent` | 确认实现逻辑正确；数据不具备时标注「待外循环验证」 |
| `manual-review` | 人工确认，记录确认结论 |

同时对照用例中的视觉验收要点（I1 占位符残留与变量泄露 / I2 弹窗缺少关闭入口 / I3 关键区域被遮挡）确认无明显缺陷。

**阻断判定**：

| 自查结论 | 后续行为 |
|---|---|
| 校验点全部满足 | 进入 Step 5.3 |
| 存在未满足项 | 影响核心功能记 P0，否则记 P1，进入 Step 5.3 分级 |
| 无用例可对照 | 记录原因后跳过，不阻断，但清单结论最高只能为「有条件通过」 |

> 自查结论写入 `.duo/{demand_description}/ui-test/self-check.md`：逐条列出校验点、是否满足、未满足原因、以及「待外循环验证」的项。

### Step 5.3：问题分级与处理

汇总 Step 5.1（Code Review）与 Step 5.2（Flow 用例自查）两路问题，统一按下表分级。

```yaml
问题分级标准:
  P0 (零容忍):
    - 编译/运行时报错
    - 核心功能不可用、白屏等严重后果
    - 数据丢失风险
    → 必须立即修复，阻塞合并

  P1 (高风险):
    - 非核心功能异常
    - 安全隐患
    - 可能影响用户体验（如性能）或代码质量劣化
    → 建议立即修复，可申请延后或说明依据

  P2 (建议优化):
    - 代码风格问题、注释缺失、可优化的写法
    → 记录到技术债，后续迭代处理

  P3 (低优/现代化建议):
    - 性能优化建议、现代化写法替换
    → 记录到技术债，不阻塞合并
```

### Step 5.4：生成验收清单

输出 `03-implementation-checklist.md`：

```markdown
# 实现验收清单

## 1. 静态检查结果
## 2. 功能验证结果
## 3. Code Review 结果
## 4. 问题清单（P0/P1/P2）
## 5. 遗留风险说明
## 6. 测试结论：通过 / 有条件通过 / 不通过
```

**章节填写说明**：

| 章节 | 内容来源 |
|------|---------|
| 2. 功能验证结果 | Step 5.2 产出的 `.duo/{demand_description}/ui-test/self-check.md`：校验点总数、满足数、未满足项及原因、待外循环验证项。Step 5.2 被跳过时写明跳过原因。**本阶段不执行自动化测试**，端到端验证由外循环完成 |
| 3. Code Review 结果 | Step 5.1 产出的 `fe-ai-review` 报告 |
| 4. 问题清单 | Step 5.3 汇总后的分级结果（含 CR 与用例自查两路） |

---

## 验证结论判定

| 结论　　　　　 | 条件　　　　　| 后续动作　　　　　　　　 |
| ----------------| ---------------| --------------------------|
| **通过**　　　 | 无 P0/P1 问题 | → 进入 Stage 6　　　　　 |
| **有条件通过** | 有 P1 但无 P0 | → 用户确认后进入 Stage 6 |
| **不通过**　　 | 存在 P0 问题　| → 返回 Stage 4 修复　　　|

> **补充约束**：Flow 用例自查（Step 5.2）存在未修复的 P0 未满足项时，结论 MUST_NOT 为「通过」；Step 5.2 因无用例可对照而跳过时，结论最高为「有条件通过」。
>
> 本阶段结论仅代表**内循环自查通过**，不等于端到端测试通过。`data-dependent` 与 `manual-review` 类校验点的最终验证由外循环完成。

---

## 异常处理

| 场景 | 处理方式 |
|------|----------|
| 无法启动本地服务 | 检查端口占用、依赖完整性；仍不可用则改为阅读代码完成 Step 5.2 自查 |
| 用例校验点依赖真实数据、无法自查 | 标注「待外循环验证」，不阻断内循环 |
| Mock 数据不足 | 补充 mock 场景或使用真实环境 |
| 测试环境不可用 | 跳过集成测试，加强静态检查 |
