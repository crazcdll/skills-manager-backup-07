## 检查工作流程
### 步骤 0: 清理工作区
检查用户的.spec目录，下面是否有已经过时的文件，以及你要使用的几个目录：`.spec/file`;`.spec/result`先做一下清理

### 步骤 1: 创建鸿蒙依赖信息对照表
提取 `oh-package.json` 中的依赖信息，按照 `dependencies`、`devDependencies`、`resolutions` 字段分别创建表格（表格名称：tabelOhPackage-dep），整理相关内容到${{outputFile:.spec/file/tabelOhPackage-dep.md}}中。

**表格列定义：**
- 依赖名称
- 当前版本（`oh-package.json` 中实际使用的版本）
- 鸿蒙支持最新版本（严格与知识库中相同，也包含^等信息）
- 是否支持 Android/iOS（是/否）

**查询与填写规则：**
- 依据参考文档第一列“依赖名称”进行完全匹配查询，严禁模糊匹配。
- 若文档中存在该依赖，取“版本号”列的值作为“鸿蒙支持最新版本”。
- 若文档中说明该版本支持三个系统，则“是否支持 Android/iOS”填“是✅”，否则填“否❌”。
- 若文档中不存在该依赖，“鸿蒙支持最新版本”留空，提示用户重点关注。
<example>
| 依赖名称| 当前版本| 鸿蒙支持最新版本| 是否支持Android/iOS|
|---|---|---|---|
| 示例：@max/meituan-uni-knb| 2.0.13| ^2.0.14| 是✅|
| 示例：@mrn/mrn-cli| 4.0.0-beta.26| 4.0.1| 否❌|
</example>


### 步骤 2: 创建通用依赖信息对照表
提取 `package.json` 中的依赖信息，按照 `dependencies`、`devDependencies`、`resolutions` 字段分别创建表格（表格名称：tabelCommonPackage-dep），整理相关内容到${{outputFile:.spec/file/tabelCommonPackage-dep}}中。

**表格列定义：**
- 依赖名称
- 当前版本（`package.json` 中当前使用的版本）
- 三个系统都兼容的版本（与知识库中）

**版本取值规则：**
- 关联步骤 1 中生成的鸿蒙依赖表，查找同名依赖。
- 如果鸿蒙依赖表中“是否支持 Android/iOS”为“是”，则将鸿蒙依赖表中的“鸿蒙支持最新版本”填入本表的“三个系统都兼容的版本”列。
- **冲突解决**：当鸿蒙依赖表中存在多个同名依赖时，以 `resolutions` 字段下的内容为准。
- 其他情况（不支持或不匹配）不填值。
- 如果知识库的依赖表中记录的为模糊版本，例如^2.0.14，按照原样记录，也记录为^2.0.14。
- 若文档中三个系统都兼容的版本为空，提示用户重点关注。
- @max/meituan-uni-xx 可用的最新版本不同，不要被误导

<example>
| 依赖名称| 当前版本| 三个系统都兼容的版本|
|---|---|---|
| 示例：@max/meituan-uni-knb| 2.0.13| ^2.0.14|
| 示例：@mrn/mrn-cli| 3.0.8| - |
</example>

### 步骤 3: 汇总特殊情况与建议

## 工作边界

工作范围：
- 读取并解析 `package.json` 和 `oh-package.json` 文件内容。
- 依据指定的参考文档进行依赖版本查询和匹配。
- 生成结构化的依赖对照表格。

不应该做的事情：
- 不进行模糊匹配，必须严格按照依赖名称完全匹配。
- 不随意猜测或修改未在参考文档中列出的依赖版本。
- 不执行实际的依赖安装或构建命令。
- 不对参考文档中不存在的依赖做主观判断，仅提示用户。
</boundary>

## 执行约束

**执行方式**
- 必须严格按照字段分类（dependencies、devDependencies、resolutions）生成表格。

- 遇到同名依赖冲突时，严格遵循“resolutions 字段优先”的原则。

**输出质量要求**
- 表格格式必须清晰，列名与步骤定义保持一致。
- 对于未在文档中记录的依赖，必须在最后明确列出提示。

**沟通风格**
- 使用结构化的 Markdown 表格展示结果。
- 保持客观、精准的描述，不添加无关建议。
