# 存储高可用规范

## 一、说明

本规范定义了 MySQL 存储操作的高可用标准，涵盖索引与查询性能、事务安全、数据安全和连接池管理四个领域。DB 资源耗尽类故障占 COE 的 6.9%，是高可用体系中需要重点防护的领域。

本规范的关注维度是”如何防止数据库操作引发系统级故障”，与 DB-01~DB-04（关注”如何正确编写 SQL 和使用 ORM”）形成互补。DB 规范解决的是 SQL 写得对不对，本规范解决的是 SQL 执行会不会把系统搞崩。其中 HA-S001 的全表扫描、列表查询 LIMIT、前缀 `%` 的 LIKE、NOT IN/NOT LIKE 等规则与 `DB-02-MySQL-SQL开发规范.md`、`DB-04-MySQL-索引规范.md` 存在内容交集，DB 规范侧重 SQL 编写正确性，本规范侧重防止慢查询拖垂系统；IN 元素数量、深分页游标分页等编写正确性要求详见 `DB-02` N006、`DB-04` N008。

## 二、规则内容

### HA-S001 [强制] 查询必须受限且避免慢查询

禁止全表扫描、无 `LIMIT` 的列表查询，以及易导致慢查询的前缀 `%` 的 `LIKE`、`NOT IN`、`NOT LIKE` 条件。

**说明**：
- 为识别慢查询，建议使用 `EXPLAIN` 验证执行计划
- 禁止全表扫描
- 返回多行的列表查询必须设置 `LIMIT` 上限
- 禁止使用前缀为 `%` 的 `LIKE` 查询（包括 `%keyword`、`%keyword%`）；后缀匹配应新增倒序字段并使用右模糊匹配，包含匹配的大数据量场景应使用 FULLTEXT 等检索能力
- 禁止使用 `NOT IN` 或 `NOT LIKE`；优先使用 `NOT EXISTS`、`LEFT JOIN ... IS NULL` 或字段值范围条件替代

### HA-S002 [推荐] 事务建议最小化且不含外部调用

事务范围建议尽可能小，事务内不建议包含 RPC 调用、MQ 发送、文件 IO 等外部操作。

**说明**：
- 事务内只做数据库操作，外部调用放在事务完成后执行
- 批量操作每批次 ≤200 条（高可用角度减少锁持有时间；DB-02 N013 编写正确性要求 ≤1000，两者不冲突，高可用场景取严格值）
- `@Transactional` 建议标注在 public 方法上，且建议通过 Spring 代理调用（不建议自调用）
- 避免大事务：单个事务执行时间建议不超过 500ms

### HA-S003 [推荐] 数据操作建议可追溯和可恢复

DELETE 操作优先使用软删除（逻辑删除），物理删除建议有二次确认和备份机制。

**说明**：
- 软删除字段建议使用 `is_deleted` TINYINT(1) DEFAULT 0
- DDL 变更建议通过 RDS 平台执行，应用程序不建议执行 DDL
- 多个相关 DDL 操作应合并执行，减少锁表次数

### HA-S004 [推荐] 连接池建议规范管理

数据库连接建议通过连接池管理，连接使用后建议归还。

**说明**：
- 连接池参数（maxActive、minIdle、maxWait）建议显式配置，不建议使用默认值
- 使用 try-with-resources 确保连接归还
- 读写分离场景：写操作后的读操作建议读主库（`@MasterSlave(force=Master)`），防止主从延迟导致数据不一致
- 分库分表场景：查询条件建议携带分片键，不建议全片扫描

## 三、示例

以下示例仅用于说明规则边界与意图，不代表唯一实现方式；实际生成或审查代码时，应优先复用项目现有框架、工具类、SDK 与命名，并以是否满足规则约束为判断标准。

### HA-S002 事务安全示例

#### good case:

```java
// 事务内只做数据库操作
@Transactional(rollbackFor = Exception.class)
public void updateOrderStatus(Long orderId, int status) {
    orderMapper.updateStatus(orderId, status);
    orderLogMapper.insertLog(orderId, status);
}

// 外部调用放在事务完成后
public void completeOrder(Long orderId) {
    updateOrderStatus(orderId, OrderStatus.COMPLETED); // 事务方法
    notifyService.sendNotification(orderId);            // 事务外的 RPC
    mqProducer.send(new OrderCompletedEvent(orderId));  // 事务外的 MQ
}
```

#### bad case:

```java
// 事务内包含 RPC — 可能导致长事务和连接池耗尽
@Transactional
public void completeOrder(Long orderId) {
    orderMapper.updateStatus(orderId, OrderStatus.COMPLETED);
    userService.addPoints(orderId);     // RPC，可能超时
    mqProducer.send(new OrderEvent());  // MQ，可能阻塞
}
```

### HA-S001 查询性能示例

#### good case:

```sql
-- 查询条件命中索引，且列表结果受 LIMIT 约束
SELECT id, status
FROM order_table
WHERE user_id = #{userId}
  AND id > #{lastId}
ORDER BY id
LIMIT #{pageSize};

-- 使用 NOT EXISTS 替代 NOT IN
SELECT o.id
FROM order_table AS o
WHERE NOT EXISTS (
    SELECT 1 FROM canceled_order AS c WHERE c.order_id = o.id
)
LIMIT #{pageSize};
```

#### bad case:

```sql
-- 无 LIMIT，可能返回大量数据并耗尽应用内存
SELECT id, status FROM order_table WHERE user_id = #{userId};

-- 前缀为 % 的 LIKE 无法有效利用普通索引
SELECT id FROM order_table WHERE order_no LIKE '%2026%';

-- NOT IN 可能导致低效执行并受 NULL 语义影响
SELECT id FROM order_table WHERE user_id NOT IN (SELECT user_id FROM blacklist);

-- 无索引条件导致全表扫描
SELECT id FROM order_table WHERE DATE(create_time) = #{date};
```

## 四、规范执行要点

- ✗ 不建议事务内包含 RPC/MQ/文件 IO
- ✗ 不建议不带分片键的查询（分库分表场景）
- ✗ 禁止无 LIMIT 的列表查询和全表扫描
- ✗ 禁止前缀为 % 的 LIKE，以及 NOT IN / NOT LIKE 查询
- ✗ 不建议应用程序执行 DDL
