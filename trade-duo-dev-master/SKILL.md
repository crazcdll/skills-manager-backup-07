# DUO 页面开发助手

当前支持生成组件展示 mock，以及清理根目录 `src/` 的 Git 跟踪。生成 mock 的目标是使组件在 demo 中正常展示且不因缺少数据或展示依赖报错，不承担完整业务流程模拟。

按请求选择对应流程：“生成 mock 数据”执行下文组件确认、覆盖检查及 demo 生成；“清理 src 目录”只执行文末[清理 src 目录](#清理-src-目录)，不要求组件名，也不触发 mock 流程。生成 mock 时不顺带清理 `src/`。

## 确定组件

1. **只检查触发请求的这一轮提示词是否明确提供组件名。** 包目录名、包名、导出组件名或明确的业务组件名称均可；“这个组件”“当前组件”不算组件名。未提供时，必须先询问“请提供要生成 mock 数据的组件名”，等待回复。绝不根据历史对话、当前文件、选中代码、工作目录或参考示例主动猜测。用户对该追问的回复可作为原请求的组件名继续处理。
2. 确定当前项目根目录，在其 `material/packages` 中查找组件。目录不存在时说明情况并询问正确项目位置；不要改用其他仓库。仅在此目录内收集候选，使用真实包目录名、`package.json` 的 `name`，以及源码确认的组件导出名参与匹配。
3. 计算每个候选与用户组件名的匹配度，取最高的一个。使用可复核的名称比较，不凭业务印象编造百分比：
   - 将 CamelCase 拆词、统一小写，以连字符等分隔符分词。候选目录至少两个时，识别全部候选目录共同的最长词前缀，并确保移除后每个候选都仍有业务词；这是项目公共前缀，例如 `hotel-dynamic-submit`。从候选标识和用户名称中移除相同前缀（存在时），避免公共前缀使不同业务组件获得虚高分数。没有可确认的公共前缀时保留原词。
   - 拼接剩余词，对用户名称与每个候选标识分别计算 `100 × (1 - Levenshtein 编辑距离 / 两者最大字符长度)`，候选分数取其各标识的最高分。完全一致为 100%。不得额外删除业务词或擅自翻译名称以抬高分数；中文名称仅使用源码或包元信息中明确的名称、别名比较，无法可靠匹配时走确认分支。
4. 最高分**严格大于 80%**且唯一时，直接进入该组件的 demo 覆盖检查，按检查结果生成或补齐，简要告知命中的名称和路径。最高分小于或等于 80%（包括恰好 80%）时，只给出最接近的一个组件及路径，询问“是否为这个组件生成 mock 数据”，等用户明确确认后再进入覆盖检查。判断阈值使用原始分数，不先四舍五入。
5. 最高分并列时说明重名情况并请用户明确目标，不任选一个。没有候选时说明未找到组件并请用户提供准确名称或路径。在缺少名称、等待组件确认或目标不明确期间，不写入 demo 或 mock。

## 先检查已有 demo

- 选定组件后，先检查其 `demo/index.ts`、`demo/index.tsx` 及入口导入的 mock 文件。结合组件入口、`types` 定义、渲染分支及直接使用的子组件、hooks、context，建立“类型字段 / 展示场景 → 已有 mock / 渲染实例”的对应关系。
- 检查必填、可选、嵌套字段及联合类型分支，覆盖源码中所有适用的展示场景和字段，并检查正常、边界场景是否有独立 mock / 实例，以及页面是否支持纵向滚动。覆盖可分布在多份 mock 与多个实例中；互斥字段无需放入同一对象，也不要求穷举所有字段组合。非展示字段和不适用的边界逐项说明理由，避免直接忽略可选字段或未使用字段。
- 确认缺失时，保留已有有效场景，自动增补缺少的数据、mock、渲染实例或滚动布局，再执行下文验证。不存在 demo 时直接新建。
- 已有数据和实例已覆盖所有适用展示场景、字段及边界，且滚动布局符合要求时，告知当前覆盖情况及类型检查、渲染验证状态，询问用户下一步要做什么并等待；不写文件。证据不足或无法验证的项目必须列为待确认，不能因此宣称完整，也不能凭猜测重写已有 demo。

## 根据类型和源码准备数据

- 追踪实际访问的嵌套字段、数组、枚举、回调和默认值；不能只看类型文件猜字段。
- 为可见内容提供最小而完整的数据。类型可选但源码无保护读取的字段也应补齐；数组内容、数量字段、状态标志和关联数据保持一致。正常场景根据真实分支选择能展示内容的值，避免合法但只会返回空内容的数据。
- **每次生成必须提供多份独立命名的 mock**，至少一份正常数据，并为适用边界分别提供数据与渲染实例，不能只生成正常场景。按真实字段和源码支持选择边界，例如名称超长换行、多行文本、可选字段缺失、空 / 单条 / 多条列表、合法零值或数量边界、长数字 / 金额，以及图片缺失或加载失败；不得捏造组件没有的字段或状态。每份数据聚焦可识别的边界，不要求所有排列组合。
- 每份 mock 显式使用实际 Props 类型，例如 `const hotelMockData: GuestCardProps = { ... }`。使用项目 TypeScript 版本支持的语法，遵循真实联合类型、枚举和函数签名。不得用 `any`、强制类型断言、`@ts-ignore` 或放宽类型定义绕过错误。
- 字段缺失场景仅省略类型允许且源码能处理的字段，不故意删除必填字段制造类型错误或渲染崩溃。源码不能处理的异常记录为未支持或风险，不修改业务源码，也不将其标为验证通过。
- 必需回调可以提供符合签名的空操作或本地状态更新。若展示依赖 provider、环境适配或初始化，优先复用项目现有 demo 方式，在 demo 范围补齐；不得为了展示修改业务源码或调用真实提单、支付、提交等服务。无法在 demo 范围解决的依赖应明确说明。

### 境外活包套餐参考数据

仅当通过 Git remote 或项目元数据确认当前仓库为 `hotel-dynamic-package-order-submit`，且当前需求明确属于“境外活包套餐”时，按需读取 [提单预览响应](references/overseas-dynamic-package/order-preview.json) 和 [预订规则与游客列表](references/overseas-dynamic-package/travelers.json)。worktree 或本地目录名称的后缀不改变仓库身份，但不能仅凭目录名判断。其他仓库、其他需求不套用；需求不明确时不擅自使用。

两份数据仅作业务样例，仍以目标组件的 types 与实际源码为准；将服务端响应映射为真实 Props 后再用于 demo，不直接把整份响应传给组件，也不擅自修正原始业务样例。本参考不替代组件名确认和已有 demo 场景、字段覆盖检查。

## 生成 demo

新建入口固定为目标组件包下的 **`demo/index.tsx`**，与参考文件命名一致。已有合法 `demo/index.ts` 或 `demo/index.tsx` 时沿用其入口，按项目实际 JSX 支持方式组织渲染；不要另建重复入口。保留已有 demo 的有效场景并增补或修正，避免直接覆盖已有内容。

参考实现为 `hotel-dynamic-submit-guest-card/demo/index.tsx`，原始位置：

```text
/Users/crazcdll07/coder/meituan-code/hotel-dynamic-package-order-submit-1/material/packages/hotel-dynamic-submit-guest-card/demo/index.tsx
```

该文件可访问时阅读其当前实现；其他环境不依赖这个绝对路径，按以下已确认模式及目标项目现有 demo 约定实现：

- 从 `../src/index` 导入真实业务组件，从实际类型定义位置导入 Props 类型。
- 将不同场景的数据分别定义为有类型的对象。参考中为 `hotelMockData: GuestCardProps` 和 `ticketMockData: GuestCardProps`，分别展示酒店入住人与门票游客两种互斥业务。
- 默认导出 demo 渲染入口，通过 `{...mockData}` 将数据传给真实组件；使用当前项目的容器、样式和框架约定。参考使用 `@hfe/max-view` 与 `remStyleSheet`，目标项目未采用时不要照搬依赖。
- demo 根部或外层页面必须支持纵向滚动，使用项目平台支持的滚动容器或既有页面滚动布局，使多个组件形成长页面后仍能滚动访问底部场景。检查固定高度裁剪和嵌套滚动冲突；按实际框架能力实现，不给 MAX 组件强塞 DOM 专用标签或 CSS。
- 多个状态或业务分支可以在同一个 demo 中渲染多个组件实例，每个实例传入独立 mock，配上必要间距或场景说明。互斥状态分别展示，不在同一份数据中混合。覆盖检查确认的全部适用展示场景和字段，不扩成业务端到端测试。
- 简单数据可像参考一样直接放在入口文件中。数据较多时按场景拆成多份 mock 文件，优先遵循目标包既有命名；没有约定时使用 `demo/mock.<scenario>.ts`，例如 `mock.hotel.ts`、`mock.ticket.ts`，再由实际 demo 入口导入。

### demo 竖向滚动

生成或检查滚动布局时，读取 [竖向滚动参考](references/scrollable-demo.md)；完整 demo 源码见 [index.tsx](references/scrollable-demo/index.tsx)。参考保存了用户确认 iOS 可用的单文件方案，不依赖手动修改共享预览工程。

- **滚动所需的高度约束随 demo 一起交付。** 先检查实际预览页导航及父布局；父容器已正确分配剩余空间时可使用 `ScrollView flex: 1`。若默认预览在固定导航下仍给内容 `height: 100%`，仅加 flex 无法避免底部裁剪，应在 `demo/index.tsx` 内限制滚动视口的可用高度。
- 对参考中的默认 Leez NavigationBar（内容高度 44、`safeArea='normal'`），用同源工具计算 `getScreenHeight('window') - toPx(44) - getSafeAreaMarginTop() - getBottomSpace()`；以 `toRem` 转回 `remStyleSheet` 输入单位，设置 `height`、`flexGrow: 0`、`flexShrink: 1`。44 必须有目标导航源码依据；导航主题、预览模板或框架不同时重新核对，不把此值作为通用常量。
- ScrollView 内的普通内容 View 按内容自然增长，多实例使用 margin/padding 分隔；不把内容固定成一屏，不无故嵌套同方向滚动。核对窗口、导航、安全区的单位与坐标范围，避免重复扣减或二次缩放。
- 不将修改 `~/.duo-cli/previewpage`、全局 CLI 模板或新增原生测量辅助文件作为本参考的使用前提。`duo preview-comp` 会重建预览页；共享工程的手动修复不能代替可分发的 demo。本次已验证方案仅修改组件包的 `demo/index.tsx`。
- 用正常预览命令重新生成页面后，滚到底部确认最后一个实例完整可见、可操作；内容因校验提示变高后再次检查。类型或 lint 通过不代表滚动验证通过，未验证的端、屏幕变化或交互需明确说明。

## 验证与交付

读取项目和组件包已有的检查、预览命令及 TypeScript 配置，执行目标 demo / mock 的类型检查，确认相关文件实际包含在检查范围内。项目已有可用 demo 预览方式时，检查正常与适用边界场景的实际渲染，确认可见内容、换行 / 缺失等边界表现和运行时无报错，并滚动到底部确认末尾场景可访问；不要擅自安装依赖或改动构建配置来制造通过结果。

交付时简要列出命中组件、生成或修改的文件、正常及边界场景、滚动支持和验证结果。区分类型检查与实际渲染；若环境缺失依赖、预览不可用或检查未覆盖 demo，明确报告未验证的部分，包括未实际检查的边界渲染和底部可访问性，不宣称“已正常展示”。

## 清理 src 目录

用户触发“清理 src 目录”时执行以下独立流程。仅处理项目根目录的 `.gitignore` 和 `src/`，不匹配 `packages/src/` 等嵌套路径；清理的是 Git 跟踪，保留本地 `src/` 文件。

1. 确认项目的 Git 根目录，后续命令均在该根目录运行。先读取工作区与暂存区状态，记录已有修改，避免将他人的变更混入本次提交。
2. 检查根 `.gitignore` 是否已有独立一行 `/src/`。已有则不重复添加；没有则保留原内容，补齐换行并追加以下两行。文件不存在时新建；星号等强调标记不写入文件。

   ```gitignore
   # DUO 出码产物（仅限根目录 src/）
   /src/
   ```

3. 使用 `git ls-files -- src/` 检查索引中是否跟踪根 `src/` 下的文件，包括没有新增暂存差异的已跟踪文件，不能只查 `git diff --cached`。有结果时执行 `git rm -r --cached src`，仅从索引移除，不删除本地文件。不得使用 `-f`；失败时停止后续步骤，说明原因并保留已有修改，不强制移除或重置。
4. 仅暂存本次新增的 `.gitignore` 规则；索引中的 `src/` 移除已由上一步暂存。不使用 `git add .`；若 `.gitignore` 含已有无关修改，按变更块精确暂存本次规则，无法隔离时说明情况并暂停提交，不整文件带入他人修改。
5. 提交前复核暂存差异，仅允许本次 `.gitignore` 规则和根 `src/` 的索引移除。若存在任何无关的已暂存变更，说明需要先隔离并暂停提交，不重置、取消暂存或顺带提交他人更改。没有本次变更时告知当前已满足要求，不创建空提交。
6. 可单独提交本次变更时执行 `git commit -m '忽略 DUO 构建的临时产物'`，提交信息必须精确使用这句话，不调用其他提交信息生成流程改写。报告提交结果及本地 `src/` 保留状态；不自动推送或发布。
