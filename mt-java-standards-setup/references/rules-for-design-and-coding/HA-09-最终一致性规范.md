# 最终一致性规范

## 一、说明

本规范定义了分布式系统最终一致性的高可用标准，涵盖幂等设计、分布式事务和缓存与 DB 一致性三个领域。幂等失效是 S0 级资损故障的常见诱因，一致性设计是分布式系统的核心挑战。

## 二、规则内容

### HA-EC001 [推荐] 关键操作建议保证幂等

所有可能被重试的操作（RPC 接口、MQ 消费、定时任务）建议保证幂等性。

**说明**：
- 幂等 Key 由调用方生成，不由被调方自行生成
- 幂等检查建议先于业务执行（先查后做，且建议原子性）
- 幂等 Key 的 TTL 建议大于重试窗口（建议 ≥7 天）
- 业务执行失败时建议删除幂等 Key（否则重试会被误拦截）
- 实现方式：数据库唯一约束、Squirrel SETNX、分布式锁

### HA-EC002 [推荐] 分布式事务建议选择合适的模式

涉及多个服务的数据一致性，建议根据业务场景选择合适的分布式事务模式。

**说明**：
- **本地消息表**：最推荐的模式，业务操作和消息写入在同一个本地事务中完成
- **Saga**：长事务场景使用补偿模式，每个步骤的补偿操作建议幂等
- **TCC**：强一致性场景，Confirm 和 Cancel 建议幂等，Cancel 建议处理空回滚
- 不建议在事务内发送 RPC 或 MQ（参见 HA-S002）
- 不建议使用 2PC/XA（性能差，不适合互联网场景）

### HA-EC004 [推荐] 缓存与 DB 一致性（精简版，详见 `HA-05`）

缓存与 DB 的一致性建议遵循 Cache Aside 模式。**完整的 Cache Aside 规则（读写模式、TTL 抖动、BigKey 检查等）详见 `HA-05-缓存高可用规范.md` HA-C001。**

**本条增量（仅分布式场景特有）**：
- 删除缓存失败时建议重试（≤5 次），重试仍失败则告警
- 高一致性场景（金额/库存）建议采用「延迟双删」或消息队列补偿方案

## 三、示例

以下示例仅用于说明规则边界与意图，不代表唯一实现方式；实际生成或审查代码时，应优先复用项目现有框架、工具类、SDK 与命名，并以是否满足规则约束为判断标准。

### HA-EC001 幂等设计示例

#### good case:

```java
public OrderResult createOrder(String idempotentKey, OrderRequest request) {
    // 1. 幂等检查（原子操作）
    Boolean success = redisTemplate.opsForValue()
        .setIfAbsent(idempotentKey, "processing", 7, TimeUnit.DAYS);
    if (!Boolean.TRUE.equals(success)) {
        return OrderResult.duplicated(); // 已处理过
    }

    try {
        // 2. 业务执行
        Order order = doCreateOrder(request);
        return OrderResult.success(order);
    } catch (Exception e) {
        // 3. 失败时删除幂等 Key，允许重试
        redisTemplate.delete(idempotentKey);
        throw e;
    }
}
```

#### bad case:

```java
// 幂等 Key 由被调方生成 — 调用方无法控制
public OrderResult createOrder(OrderRequest request) {
    String key = UUID.randomUUID().toString(); // 每次调用都不同，无法去重
    // ...
}

// 幂等检查和业务执行不是原子的 — 并发时可能重复
if (!redisTemplate.hasKey(key)) {      // 检查
    doCreateOrder(request);             // 执行（两步之间可能有并发请求）
    redisTemplate.set(key, "done");     // 标记
}
```

## 四、规范执行要点

### 不建议做法
- ✗ 不建议幂等 Key 由被调方自行生成
- ✗ 不建议幂等检查和业务执行非原子
- ✗ 不建议在事务内发送 RPC 或 MQ
- ✗ 不建议使用 2PC/XA

### 代码审查检查点
- [ ] 可重试接口是否保证幂等
- [ ] 幂等 Key 是否由调用方生成
- [ ] 幂等检查是否原子性
- [ ] 跨服务一致性是否有明确的事务方案
