# 处置报告与记忆

> **执行顺序**：① 前置校验 → ② 时间准备 → ③ 生成报告 → ④ 反馈收集 → ⑤ 写入记忆 → ⑥ 自查确认

---

## ① 前置输入校验

本 skill 作为全流程第六步执行，**必须**在 S1-S5 全部完成且输出结果已确认后方可执行。

> 🚨 **禁止在缺少前五步输出时生成报告。** 如果前五步的任何一步没有输出结果，**不得自行编造或推断**，必须先回到对应步骤执行完成后再生成报告。

### 依赖检查

执行报告生成前，**必须**逐项确认以下输入：

| 输入项 | 来源 | 必须非空 | 缺失时处理 |
|--------|------|---------|----------|
| 信号类型、业务线、Bundle/页面 | 第一步·信息提取 | ✅ | 回退到 S1 执行 |
| 变更扫描结果 | 第二步·变更查询 | ✅ | 回退到 S2 执行 |
| 止损操作记录 | 第三步·止损操作 | ✅（含跳过场景） | 回退到 S3 执行 |
| 排查结论 | 第四步·排查结论 | ✅ | 回退到 S4 执行 |
| 修复方案 | 第五步·修复方案 | ✅ | 回退到 S5 执行 |

### 检查流程

```
开始生成报告前：
  ├─ 逐项检查 S1-S5 的输出是否存在且非空
  │    ├─ 全部存在 → 继续
  │    └─ 任一缺失 → 停止，告知用户「第 X 步输出缺失，无法生成报告」
  │         → 提示先执行/完成该步骤后再生成报告
  │         → **不得自行编造缺失内容**
  └─ 确认状态管理 JSON 中 S1-S5 均为 completed
       ├─ 是 → 继续
       └─ 否 → 提示用户状态不完整，先补全
```

> ⚠️ **状态管理守卫**：`state-manager.sh read <issue_id>` 显示 S1-S5 必须全部为 `completed`，才能执行 S6。如果 Agent 未走状态管理直接到达此步，**必须**先提示用户执行 `init` + 补全 S1-S5 的状态记录。

## ② 时间获取与耗时提取

### 获取当前时间

在输出报告之前，**必须**先执行以下命令获取当前真实时间，用于填充报告中所有 `{生成时间}` 和第六步记录的时间戳：

```bash
date "+%Y-%m-%d %H:%M"
```

将命令输出结果（格式如 `2026-04-30 14:35`）赋值给 `REPORT_TIME`；严禁用会话上下文推断时间。

### 提取各步骤完成时间和耗时

**处置时间线中每步的完成时间和耗时必须从对应步骤的输出标题中提取，不得估算或推断。**

| 步骤 | 标题格式示例 |
|------|-------------|
| 第一步 | `✅ **第一步：信息提取报告**（完成时间：2026-04-30 14:23:05  耗时：约 3 分钟）` |
| 第二步 | `✅ **第二步：变更查询报告**（完成时间：2026-04-30 14:28:12  耗时：约 5 分钟）` |
| 第三步（止损） | `🛑 **第三步：止损操作报告**（完成时间：2026-04-30 14:30:00  耗时：约 2 分钟）` |
| 第三步（跳过） | `🟢 **第三步：跳过止损报告**（完成时间：2026-04-30 14:28:15  耗时：约 1 分钟）` |
| 第四步 | `✅ **第四步【路径A】：告警排查结论**（完成时间：2026-04-30 14:46:33  耗时：约 18 分钟）` |
| 第五步 | `✅ **第五步：修复方案（xxx）**（完成时间：2026-04-30 14:56:59  耗时：约 1 分钟）` |

提取规则：

- **完成时间**：取 `完成时间：` 后的时间字符串；在报告中显示为 `HH:MM`。
- **耗时**：取 `耗时：` 后的字符串并原样填入。
- 缺失时填「—」，**严禁自行估算**。

## ③ 生成报告

### 格式要求

1. 报告必须严格按「问题总结」在前、「处置时间线」在中、「每一步详细结果」在后的顺序输出；不得将详细证据混入问题总结。
2. **【问题总结】必须使用完整表格**，每行一个字段，不得改成文字段落。
3. **【处置时间线】必须使用 5 列完整表格**（步骤 / 完成时间 / 耗时 / 操作内容 / 执行人），前五步各占一行。
4. **【每一步详细结果】必须按第一步至第五步依次直接引用前置 Skill 的完整输出**，不得二次提炼、改写、拆分字段、套用新模板或遗漏内容；即使止损跳过，也必须原样保留第三步的跳过结果。
5. 除报告标题、问题总结和处置时间线外，前五步内容保持其原有标题层级和 Markdown 格式。
6. **🚨 报告输出终止规则（最高优先级）**：报告的完整输出仅包含三个部分——「问题总结」+「处置时间线」+「每一步详细结果」。第五步详细结果输出完成后，**必须立即输出反馈询问**（见 ④ 反馈收集），然后停止。**严禁在报告之后、反馈询问之前或之后追加任何额外内容**，包括但不限于：整体总结、处置总结、核心结论、关键发现、一句话概括、要点回顾、后续建议（已在问题总结「后续动作」字段中的除外）。报告 + 反馈询问即为本次输出的全部内容，不得包裹任何额外的概述或收尾文字。

## ④ 反馈收集

> 🚨 **报告生成后必须执行此步骤，不可跳过。** 报告输出 + 反馈收集 + 写入记忆是一个原子操作，三者必须连续完成。

### 执行流程

```
报告输出完成
  │
  ├─ 步骤 1：输出报告完整内容（问题总结 + 处置时间线 + 前五步详细结果）
  │    ⚠️ 报告内容到此为止。禁止在第五步详细结果之后追加任何总结、概述、
  │    核心结论、处置摘要、关键发现、要点回顾等额外内容。
  │
  ├─ 步骤 2：在报告下方紧接着输出反馈询问（必须）
  │    ⚠️ "紧接着"意味着报告最后一个 `---` 分隔线之后直接输出反馈询问，
  │    中间不得插入任何段落、表格、列表或文字。
  │    → 使用以下固定格式：
  │    ┌──────────────────────────────────────────────────────┐
  │    │ 📋 以上为本次稳定性处置报告。                       │
  │    │ 请确认本次排查是否有效？请选择「有效」或「无效」。  │
  │    └──────────────────────────────────────────────────────┘
  │
  ├─ 步骤 3：等待用户反馈
  │    ├─ 用户回复「有效」 → 写入记忆，标题标 【反馈：有效】
  │    ├─ 用户回复「无效」 → 写入记忆，标题标 【反馈：无效】，记录失败原因和改进方向
  │    ├─ 用户回复「未评价」或拒绝评价 → 写入记忆，标题标 【反馈：未评价】
  │    └─ 用户未回复 → 提示「请回复有效/无效以完成报告归档」后，记为【反馈：未评价】并完成 S6
  │         （用户未回复不阻塞 S6 完成，后续用户补充反馈时可更新记忆）
  │
  └─ 步骤 4：写入记忆后，简短确认「已记录本次{有效/无效/未评价}处置经验」
       ⚠️ 不得在确认语之后再追加总结、回顾或任何额外内容。
```

> ⚠️ **如果 Agent 跳过反馈收集直接写入记忆，视为执行失败。** 反馈标签必须来自用户的真实回复，不得由 Agent 自行判断。

## ⑤ 写入记忆

先读取 `memory` skill，并严格遵循其中的存储策略；稳定性处置经验属于本技能的领域知识，应优先追加到本技能的「学习笔记」。

### 记录原则

- 仅记录经排查确认、可复用于后续处置的事实：根因模式、关联变更特征、止损有效性、修复方案、排查证据和责任边界。
- 不记录完整告警原文、用户标识、订单号、traceId、敏感日志、密钥或临时链接。
- 用户标识如确需说明，使用脱敏摘要；不记录可回溯的个人信息。
- 每个问题追加一条独立记录；若结论为待确认，明确标注待确认项和后续验证条件。
- 标题必须包含提问者反馈标签：`【反馈：有效】`、`【反馈：无效】` 或 `【反馈：未评价】`；不得遗漏或使用其他表述。
- 反馈为「无效」时，仍完整记录本次根因、处置与失败/不符合预期的原因，并在复用建议中明确改进方向。

### 追加格式

在本 `SKILL.md` 末尾的 `## 学习笔记` 章节中追加以下内容；章节不存在时创建：

```markdown
### 【反馈：有效 / 无效 / 未评价】[{YYYY-MM-DD}] {业务线}｜{页面或 Bundle}｜{问题短标题}
- **提问者反馈**：{有效 / 无效 / 未评价；如有补充意见，使用脱敏摘要记录}
- **信号与影响**：{信号类型、影响范围的脱敏摘要}
- **根因**：{已确认根因；未确认时标注「待确认」及验证条件}
- **关联变更**：{Diva / MCM 变更对象与关联结论；无则写「未发现相关变更」}
- **止损与修复**：{是否止损、有效性、修复方式；不包含内部链接和敏感标识}
- **复用建议**：{下次优先检查的版本、组件、接口、监控或操作步骤；反馈无效时写明改进方向}
```

写入完成后，在最终回复中简短说明「已记录本次{有效 / 无效 / 未评价}处置经验」，不要展示或重复敏感信息。
