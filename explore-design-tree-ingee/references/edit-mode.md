# D2C Edit Mode：如何让 Agent 正确地迭代已有模块

> **TL;DR**
> 原有 D2C 工作流是为"从零开始"设计的，在迭代已有模块的场景下表现不佳。我们通过三轮迭代，最终实现了一套"视觉优先 + 极简摘要 + Loop Guard"的 Edit Mode 工作流：
>
> 1. 底层用锚点匹配+指纹匹配建立新旧设计稿的模块对应关系
> 2. 中间用清洗脚本剥离所有结构信息，只给 Agent 极简的视觉级摘要
> 3. Agent 先看截图再看摘要，输出模块级 Edit Plan，最后通过 Loop Guard 自检拦截结构性描述
>
> 核心设计原则：**工具只给事实，不给 Agent 做结构推理的素材；宁缺毋滥，不误导。**

## 1. 背景

D2C 的编码工作流（下文称 Create Mode）是一条单向管线：

```
设计稿 URL → 序列化 JSON → 规划模块 → 逐模块编码 → Diff → 完成
```

每一步都假设"前面什么都没有"。但实际业务中，更常见的场景是**设计迭代**——V1 已经实现了，设计师给了 V2 设计稿，需要更新代码。此时 Create Mode 的问题暴露得很明显：

| 能力 | Create Mode | Edit Mode 需要 |
|---|---|---|
| 识别新旧设计的差异 | ❌ | 核心需求 |
| 判断哪些模块不用动 | ❌ | 减少无效工作 |
| 代码↔设计节点映射 | 不需要 | 精准定位改动 |
| 缓存强制刷新 | 不需要 | 拿到最新数据 |

## 2. 核心挑战：新旧设计稿没有共享 ID

最初的假设是"设计迭代 = 同一个 Frame 改了几个属性，节点 ID 不变"。如果这个假设成立，diff 就很简单——按 ID 一一比对即可。

**但实际情况是：新版 UI 必然是新的设计稿，所有节点 ID 都是全新的。** 设计师不会在原来的 Frame 上改，而是复制一个新 Frame 或新建一个文档来做迭代版本。

这意味着基于 ID 匹配的 diff 方案直接废掉，问题退化为：**两棵没有共享 ID 的树，如何建立节点对应关系？**

## 3. 方案探索

### 3.1 第一轮：锚点 + 指纹匹配（match_nodes.py）

思路：两棵树虽然没有共享 ID，但有共享**内容**。最稳定的信号是文本——"¥128"、"立即预订"这些文本在 V1 和 V2 之间大概率一致。

**三轮匹配算法**：

```
Round 1: 锚点匹配 — 在两棵树中找唯一文本，建立高置信度配对
Round 2: 向上传播 — 由已配对的子节点推导父容器配对
Round 3: 容器内指纹匹配 — 在已配对容器内部，用分层指纹匹配剩余节点
```

**指纹的分层设计**：

| 层级 | 信号 | 权重 | 稳定性 |
|---|---|---|---|
| Layer 1 | 文本内容 | 10 | 最高 |
| Layer 2 | 结构（tag、children 数量、children 类型序列、节点名） | 8 | 高 |
| Layer 3 | 样式（display、flexDirection、fontSize） | 3 | 中 |
| Layer 4 | 位置（兄弟节点中的相对位置） | 1 | 低 |

匹配时逐层放宽：Layer 1+2+3 全匹配 → 同一节点且样式没变；Layer 1+2 匹配但 Layer 3 不同 → 同一节点但样式变了。

**准确率验证**：

取真实设计稿数据（1271 个节点），将新版的 ID 全部随机重映射模拟"全新设计稿"，用原始 ID 对应关系作为 ground truth：

| 难度 | 变异内容 | 正确率 | 准确率 |
|---|---|---|---|
| Easy | 纯 ID 重映射 | 100% | 100% |
| Medium | 10% 文案修改 | 100% | 100% |
| Medium | 5% 叶子删除 | 97.3% | 98.7% |
| Hard | 20% children 乱序 | 98.7% | 98.7% |
| Hard | 10% 文案 + 5% 删除 + 10 新增 | 96.7% | 99.1% |
| **Extreme** | **30% 文案 + 10% 删除 + 30 新增 + 30% 乱序** | **94.8%** | **99.1%** |

Extreme 难度下仍有 99.1% 的准确率——匹配到的节点几乎不会配错。错误集中在同名同结构的 SVG 路径节点（如多个 `路径` 节点），这些节点本身是切图，不影响编码。

### 3.2 问题暴露：输出粒度不对

第一轮实现输出的是**节点级**的 diff——278 个 style 差异逐条列出。但 Agent 需要的是**模块级**的行动指引，不是"fontSize 从 28px 变成 32px"。

重构为模块级匹配后，输出变成了 `skip / patch / new / removed / merged` 五种 action。

用真实业务数据测试（凌晨提示 → 开启定位）：

```
9 Skip / 2 Patch / 2 New / 2 Merged / 2 Removed
```

看起来合理。但当我按这个输出写 Edit Plan 时，发现一个根本问题。

### 3.3 问题暴露：工具在替 Agent 做判断

输出 `merged: 组 1776 → 容器 402973` 是在告诉 Agent "这个模块被合并了"。Agent 拿到这个信号后，自然会在 Edit Plan 中写："积分信息模块被合并到搜索区域，原来是独立模块，现在……"

**但这是设计稿内部的结构变化，不是视觉变化。** 从用户视角看，积分信息一直在那里，位置没变，样式没变——代码不需要改。工具输出的 `merged` 标签诱导 Agent 做了无意义的结构推理。

**重写为纯标注器**（annotator），去掉所有 action 判断：

| 旧版输出（做判断） | 新版输出（纯标注） |
|---|---|
| `action: "merged"` | `status: "before_only"` + `text_absorbed: {coverage: 1.0}` |
| `action: "skip"` | `status: "matched"` + `facts: {structure_same: true, ...}` |
| `action: "patch"` | `status: "matched"` + `facts: {texts_added: [...], ...}` |

### 3.4 问题仍然存在：数据本身在诱导结构推理

去掉 action 标签后，数据中仍然有 `text_absorbed: {absorbed_by: "容器 402973", coverage: 1.0}` 这样的交叉引用。Agent 看到这个字段，本能地就会推理"组 1776 的文本被吸收到了容器 402973"，然后在 Edit Plan 中写出结构性描述。

即使在 SKILL.md 中写了"禁止描述结构变化"，Agent 仍然违规——**因为数据本身在诱导这种推理**。

**根因**：不是 prompt 写得不够好，是数据流设计有问题。

### 3.5 最终方案：三层架构 + Loop Guard

```
Layer 1: match_nodes.py (底层标注器，Agent 不可见)
    ↓
Layer 2: visual_diff.py (清洗层，剥离所有交叉引用)
    ↓
Layer 3: Agent 看截图 + 极简摘要 → Edit Plan → Loop Guard
```

**visual_diff.py 的清洗规则**：

| 保留 | 剥离 |
|---|---|
| unchanged / changed / new / gone 四类 | ~~matched / before_only / after_only~~ |
| 模块名、nodeId、节点数 | ~~similarity 分数~~ |
| 文本预览 | ~~texts_added / texts_removed 对比~~ |
| 变更程度（minor/major） | ~~structure_same 标志~~ |
| — | ~~text_absorbed 交叉引用~~ |

**清洗后的输出示例**（凌晨提示 → 开启定位）：

```json
{
  "unchanged": [{"name": "酒店头图", "id": "714:182292"}, ...],
  "changed": [{"name": "容器 403066", "id": "714:196994", "level": "major", "nodes": 212}],
  "new": [{"name": "容器 35049", "id": "714:182271", "texts": ["开启精确位置…", "开启"]}],
  "gone": [{"name": "容器 35049", "texts": ["当前时间已过", "0", "点，已选择今天凌晨"]}]
}
```

没有任何字段能让 Agent 推理"A 模块的内容被移到了 B 模块"。Agent 只能看截图判断视觉差异。

**Loop Guard 自检清单**：

Agent 输出 Edit Plan 后，必须自检以下违规项：

- ❌ 描述设计稿内部的层级变化（"从容器 A 移到容器 B"）
- ❌ 引用 before 侧的 nodeId 来描述 after 侧的模块
- ❌ 使用结构性动词：合并、拆分、提取、重组、吸收、移动
- ❌ 解释 new/gone 条目之间的对应关系
- ✅ 只描述视觉效果的变化
- ✅ 只描述代码需要做的事

## 4. 验证

### 两组真实业务设计稿测试

| 测试对 | 场景 | unchanged | changed | new | gone | Agent 违规 |
|---|---|---|---|---|---|---|
| 凌晨提示 → 开启定位 | 小改动 | 9 | 2 | 2 | 4 | 0 |
| 真便宜列表页 → 特价酒店-学生 | 大改版 | 1 | 1 | 9 | 19 | 0 |

### Agent 输出质量对比

**无 Loop Guard 时的典型违规**：

> "日期+搜索综合区域 (id: 714:182407)
> 新增了"找 酒 店"入口和"订酒店得10倍积分"信息展示。**原来这两部分是独立模块，现在视觉上合并为一个区域。**"

**有 Loop Guard 时的输出**：

> "日期+搜索区域 (id: 714:182407)
> 变化：新增了"找酒店"入口和积分信息展示
> 行动：inspect 新版节点，补充新增元素"

### gone 条目的正确处理

visual_diff 输出 `gone: 容器 153076 (找酒店)` 和 `gone: 组 1776 (积分信息)`。在旧方案中 Agent 会说"这两个模块被合并到了容器 402973"。

在新方案中，Agent 看截图发现"找酒店"按钮和积分信息**在两版中都可见**，因此判断为"不动"，直接归入 unchanged。没有做任何结构推理。

## 5. 迭代过程中的关键决策

### 为什么不让工具直接输出模块级计划？

我们尝试过让工具输出 `skip / patch / new / removed` 的 action 判断。问题是：

1. **缺少视觉上下文**：工具只看 JSON 结构，不看截图。结构上"新增"的模块可能视觉上一直都在
2. **缺少代码上下文**：工具不知道哪些组件已经实现了、文案是硬编码还是接口返回的
3. **武断的判断会误导 Agent**：Agent 倾向于信任工具输出的 action，即使它看截图觉得不对

正确的分工：**工具只负责"看到了什么"，Agent 负责"应该怎么做"**。

### 为什么要清洗掉交叉引用？

`text_absorbed: {absorbed_by: "容器 402973", coverage: 1.0}` 这个字段看起来很有用——它告诉 Agent "这些文本还在，只是换了个位置"。但实践中发现，Agent 拿到这个信息后**必然会**在输出中描述"A 被合并到了 B"，无论 prompt 怎么写都挡不住。

原因：这个字段的信息密度太高，Agent 认为不提它就是浪费信息。唯一有效的方式是**不给它**。

### 为什么 Loop Guard 是自检而不是工具校验？

考虑过用正则匹配 Agent 输出中的结构性动词（合并/拆分/提取），自动拒绝。但结构性动词有时在描述视觉变化时是合理的（如"筛选栏从 4 项变为下拉"），硬性禁止会误杀。

自检的优势：Agent 理解上下文，能区分"描述视觉变化"和"描述结构重组"。checklist 式自检在实践中比规则引擎更准确。

## 6. 最终架构

```
用户给出 before + after 设计稿 URL
    ↓
Step 1: 下载两个 Frame（download_ingee.py --image-id ... --frame-id ...）
    ↓
Step 2: visual_diff.py → 极简摘要（unchanged/changed/new/gone）
    ↓
Step 3: Agent 看截图（视觉优先）+ 摘要（辅助确认）+ 代码（判断能否复用）
    ↓
Step 4: 输出 Edit Plan（不动/更新/新增/删除）
    ↓
Step 5: Loop Guard 自检 → 通过 → 执行 | 违规 → 重写
```

**核心代码**：

| 文件 | 行数 | 职责 |
|---|---|---|
| match_nodes.py | 390 | 底层标注器（锚点+指纹匹配），Agent 不直接使用 |
| visual_diff.py | 134 | 清洗层，剥离结构信息，输出极简摘要 |
| diff_report.py | 366 | HTML 可视化报告（供人工 review） |
| SKILL.md | +136 | Edit Mode 工作流（6 步骤 + Loop Guard） |

## 7. 已知局限

1. **模块深度固定**：当前默认取 root 的直接子节点作为模块粒度（depth=1），对于嵌套较深的设计稿可能粒度太粗
2. **gone 列表碎片化**：大改版场景下 gone 可能有 19 个条目，Agent 需要手动合并。可考虑在 visual_diff 层做基于文本/节点数的聚合
3. **visual_diff 丢失了有用信息**：`text_absorbed` 虽然会诱导结构推理，但它确实能帮助 Agent 判断"这个 gone 模块的内容是否还在"。当前完全剥离的做法在信息量和安全性之间选择了安全性，可能在某些场景下让 Agent 做出次优判断
4. **Loop Guard 依赖 Agent 自觉**：自检不是强制的，理论上 Agent 可以跳过。如果发现实践中违规率仍然较高，可以考虑加入工具级校验作为补充
