# Step 01：使用 ee-mep 获取仓库信息，拉取并校验清单文件

## 输入

- `repoUrl`：用户提供的 DUO 配置仓库（ssh）
- `branch`：用户提供的开发分支

## 目标

1. 通过 `ee-mep`（`mep code`）获取目标仓库信息（可访问性/仓库配置等）
2. 获取 `repoUrl` 对应 `branch` 的代码到本地临时目录
3. 校验以下文件是否存在且有效：
   - **必须存在且为有效 JSON**：`componentsMap.json`、`dependencies.json`
   - **允许缺省或为空**：`ohDependencies.json`

## 执行步骤

### 1) 准备临时工作区

在当前工作区根目录下创建临时目录（如不存在）：

- 克隆目录推荐路径：`.temp/trade-duo-projects-standard/work/`
- **结果输出目录（必须）**：`.temp/trade-duo-projects-standard/result/`（与 `work/` 同级，用于保存本 skill 全部落盘输出）

```bash
mkdir -p .temp/trade-duo-projects-standard/work
mkdir -p .temp/trade-duo-projects-standard/result
```

要求：
- 多次执行时应可复用：若同名 `work` 目录已存在，先清理该目录或换一个带时间戳的子目录。
- 不允许直接在 `trade-skills` 仓库根目录执行目标仓库的 git 操作。

### 2) 拉取目标仓库指定分支

使用 git clone 获取代码（必须 checkout 到用户指定分支）：

```bash
git clone "<repoUrl>" "<localDir>"
cd "<localDir>"
git fetch --all --prune
git checkout "<branch>" || git checkout -b "<branch>" "origin/<branch>"
```

验证：

```bash
git rev-parse --abbrev-ref HEAD
git log -1 --oneline
```

### 3) 使用 ee-mep 获取仓库信息（mep code）

在目标仓库目录内，使用 `ee-mep` 的 `mep code` 子命令获取仓库信息，用于确认仓库可访问、以及后续标准化流程的上下文（例如仓库设置/默认分支等）。

#### 3.1 安装与 Node 版本（避免直接失败）

- **`mep` 不存在**：先执行 `which mep`；若未找到，**安装后再继续**（不要立刻终止）：
  ```bash
  npm install -g @ee/mep-cli --registry=http://r.npm.sankuai.com
  ```
  安装后确认 `mep code --help` 可执行。
- **`fetch is not defined`**：当前 Node 版本低于 18，`@ee/code-cli` 需要全局 `fetch`。请**切换到 Node.js 18 或更高版本**（例如 `nvm use 18`、`nvm use 20`）后再执行 `mep code`；**不要**使用 Node 16 或 `experimental-fetch` 等变通方式。
- 仍无法运行 `mep code` 时，再报错终止（并说明已尝试安装/切换 Node）。

#### 3.2 拉取仓库设置

执行建议（若命令不确定，先查 help 再执行）：

```bash
mep code --help
mep code repo --help
mep code repo settings --help
```

**方式一（推荐）：在克隆目录内执行（依赖 git remote 自动解析仓库）**

> **必须先 `cd` 到克隆目录**，`mep code repo settings` 会读取当前目录的 `.git/config` 中的 remote origin 自动解析仓库标识，无需手写仓库路径。

```bash
cd "<localDir>"
mep code repo settings --json
```

完整示例（`localDir` = `.temp/trade-duo-projects-standard/work/duo-hotel-order-submit`）：

```bash
cd .temp/trade-duo-projects-standard/work/duo-hotel-order-submit
mep code repo settings --json
```

**方式二（备选）：通过 `-R PROJECT/REPO` 显式指定仓库（无需进入克隆目录）**

当无法 `cd` 进克隆目录时，可在任意位置使用 `-R` 选项，格式为 **`PROJECT/REPO`**（从 SSH URL 中提取，不是完整 URL）。

SSH URL → `-R` 参数的提取规则：

| SSH URL | `-R` 参数值 |
|---------|------------|
| `ssh://git@git.sankuai.com/nibfe/duo-hotel-order-submit.git` | `nibfe/duo-hotel-order-submit` |
| `ssh://git@git.sankuai.com/hfe/hotel-material.git` | `hfe/hotel-material` |

> 规则：去掉 `ssh://git@git.sankuai.com/` 前缀和 `.git` 后缀，剩余部分即为 `PROJECT/REPO`。

```bash
# 完整格式：mep code repo -R <PROJECT/REPO> settings --json
mep code repo -R nibfe/duo-hotel-order-submit settings --json
```

如需补充查看当前仓库远端信息（辅助确认 `-R` 参数）：

```bash
git -C "<localDir>" remote get-url origin
# 或进入目录后：
git remote -v
```

要求：
- `mep code repo settings --json` 若返回鉴权/权限错误，需要在本 step 中明确报错原因并终止（不要继续"假装获取成功"）。
- **成功时**：将 `mep code repo settings --json` 的**标准输出**原样写入 **`.temp/trade-duo-projects-standard/result/mep-repo-settings.json`**（仅 JSON，便于后续审计）。

### 4) 校验清单文件存在与 JSON 合法性

> 注：执行顺序为「拉取代码 → `mep code` 获取仓库信息 → 校验清单文件」。这样 `mep code` 可以通过当前目录的 git remote 自动解析仓库信息，避免手工传仓库标识。

#### 必需文件（缺失则失败）

- `componentsMap.json`
- `dependencies.json`

校验规则（两者都要通过）：
- 文件存在
- 文件内容非空（避免空文件/只含空白）
- 能被 JSON 解析（有效 JSON）

#### 可选文件（允许缺省或为空）

- `ohDependencies.json`

允许情况：
- 文件不存在
- 文件存在但为空文件
- 文件存在且为 `[]`
- 文件存在且为有效 JSON（通常为数组）

处理规则：
- 若文件不存在：为保证后续流程可落地，**在仓库根目录创建** `ohDependencies.json`，内容为 `[]`（并记录该动作用于 Step 2 的 commit message 明细）
- 若为空文件：写入 `[]`（同样记录动作）

### 5) 输出本步结果（供 Step 2 使用）

**必须**写入 **`.temp/trade-duo-projects-standard/result/step01.json`**（路径固定，勿仅依赖对话复述）：

```json
{
  "repoUrl": "...",
  "branch": "...",
  "localDir": "...",
  "hasComponentsMap": true,
  "hasDependencies": true,
  "ohDependenciesStatus": "missing|empty|present",
  "ohDependenciesPatchedToEmptyArray": true
}
```

若本 step 失败，可在 **`.temp/trade-duo-projects-standard/result/error-step01.txt`** 中写入简要错误信息（可选）。

> 注意：本 step 不做任何依赖标准化改造，只做「拉取 + 校验 +（必要时）补齐空的 `ohDependencies.json`」。
