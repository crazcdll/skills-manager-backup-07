# 输出规范

## 一、输出目标

**当前会话**（默认）：直连用户时，报告内容在会话中输出即为合法交付；无需强制落盘，但建议落盘以便复查和上游 skill 取用。

**本地 Markdown**（需要存档/落盘时）：完整报告按 [tpl-report.md](tpl-report.md) 渲染，落盘为单份文件。报告包含准备章节（审查前判断）和发现章节（审查结论），便于存档和信息同步。

---

落盘后，同步在会话中输出最小概要供上游读取。对话中展示的结论与 Markdown 文件内容一致：

```
markdown_path: <报告文件路径>
conclusion: approve | approve_with_suggestion | fix_then_merge | block
launch_risk: safe | low | medium | high
counts: p0=0 p1=0 p2&p3=0
one_line: <一句话摘要>
```

**枚举映射**（中文报告字段 ↔ 结构化摘要字段）：

| 报告「审查结论」 | `conclusion` | 报告「上线风险」 | `launch_risk` |
|---|---|---|---|
| ✅ 可合并 | `approve` | 🟩 安全 | `safe` |
| ✅ 可合并（有优化建议） | `approve_with_suggestion` | 🟨 低风险 | `low` |
| ⚠️ 修复后可合并 | `fix_then_merge` | 🟧 中风险 | `medium` |
| ❌ 不建议合并 | `block` | 🟥 高风险 | `high` |

内部先组织结构化中间结果，再渲染 Markdown。

## 二、内容约定与关键约束

报告章节顺序和填写格式见 [tpl-report.md](tpl-report.md)。以下为关键约束：

- **审查结论和问题计数**只能来自实际发现项，不得凭空填写
- **主审查集以 git 状态为准**：若工作区存在未提交变动，主审查集仍以 `staged / working_tree / commit / branch` 为准，未提交部分标注进 Open Questions（"待提交后次轮复查"）
- **发现项置信度**：P0/P1 条目置信度非高时，内联补充 `置信度：高/中/低（理由）`；P2-P3 不要求
- **规则编号**：问题类型后的 `[规则编号]` 需与实际命中的规则库条目一致，不得编造；无命中的问题不加
- **Open Questions 与低置信度的区别**：发现项是"有结论但把握不足"，Open Questions 是"看到信号但无法给结论"，结论强依赖业务上下文或人工提供的信息

## 三、自检

**落盘时自检（必须）**：写完报告后、向用户播报结论前，必须逐项过检。任一项不过则报告视为未完成：

1. **文件落盘**：Markdown 文件存在且内容不为空；否则回滚并报告写入失败。
2. **计数一致**：审查概要中各级别计数（P0 / P1 / P2-P3）与发现项下实际条目数完全吻合；不一致则修正后重新渲染。
3. **结论一致**：审查结论须与问题统计逻辑自洽（以下规则按顺序匹配，命中即停）：
   - 有 P0 → `fix_then_merge` 或 `block`
   - 无任何发现项（P0=P1=P2-P3=0）→ `approve`
   - 有 P1 无 P0：P1 条目内未标「已接受风险」的，一律 `fix_then_merge`；全部标记「已接受风险」则 `approve_with_suggestion`
   - 仅有 P2-P3，无 P0/P1 → `approve_with_suggestion`
4. **级别合法**：所有发现项的严重级别只能是 P0/P1/P2/P3（P2-P3 组内可不细分），不得出现 High/Medium/Low 等别名；出现则修正。
5. **路径合规**：上游指定报告路径时按指定路径写入；未指定时遵守命名规范。

**未落盘时等价自检（直连且用户未要求存档）**：跳过第 1 / 5 条，但第 2、3 条计数与结论必须在会话回复里自洽——没有文件不等于可以跳过结论校验。

## 四、输出风格

- **结论先行**：审查结论和高优发现项排在最前
- 按严重程度排序：P0 → P1 → P2-P3，同级内按影响范围排
- 每条发现项优先说清楚"为什么有风险"和"怎么改"，不堆砌规范条文
- 没有发现问题时，明确写"未发现明确阻塞项"，同时说明覆盖范围和未验证部分
