# AGENTS.md 创建与治理

把仓库规则从“代码的散文版缓存”改造成 Agent 的本地执行契约：先防止高代价错误，再减少搜索、对话补充和常驻上下文。

## 三类权威来源

- **代码与配置**回答“当前实际怎样实现”。依赖、目录、接口、组件、字段和状态流转以当前分支为准。
- **中央知识库或专用 Skill**回答“跨仓业务语义、团队规范、所有权和为什么”。不要把正文复制进业务仓库。
- **AGENTS.md**回答“在这里怎样安全工作、哪些动作必须执行、去哪里找权威来源”。

内容冲突时先按类型判断权威来源，不笼统规定代码或文档永远优先。

## 开始前

1. 确认目标仓库、目标包或目录、任务范围、当前分支、工作区和已有改动。保护用户改动，不自动 stash、覆盖或清理。
2. 读取目标目录及祖先目录中适用的 `AGENTS.md`、`CLAUDE.md`、`.cursorrules`、`CONTRIBUTING.md` 和仓库规则。若用户要求隔离分支，当前分支已明显属于 agents/docs 治理则直接使用；否则再按仓库约定创建分支。
3. 机械枚举目标范围内所有 `AGENTS.md`、`CLAUDE.md`、README、manifest 和相关生成配置，记录行数与字节数。
4. 用户未指定目标目录时，从当前目录向上查找最近的项目清单，例如 `package.json`、`go.mod`、`pyproject.toml`、`Cargo.toml` 或 `pom.xml`；存在多个合理目标且会改变结果时再询问，不猜测。
5. 读取当前规则全文，并用当前源码、manifest、构建配置和运行结果核验其中的事实。旧文档、旧分支和历史总结只能提供检查线索。

## 选择规则层级

- **普通单包仓库**：根 `AGENTS.md` 提供完整行动契约。
- **共享规则明确的 Monorepo**：根文件放通用路由和约束，子级文件只补本目录差异，不复制父级。
- **页面由不同团队独立维护、没有可靠共同约束的单仓多页面项目**：根文件只做路由；每个页面可以有自包含的完整 `AGENTS.md`，但不得引用兄弟页面的实现结论。页面通常是最细粒度。
- **生成物工程或同目录存在不同发布生命周期**：根文件写源码/生成物边界，并为协议、物料、构建器等真正不同的工作单元设置子级规则。

不要因为模板要求而创建空洞的子级文件。选择或编写具体结构时，读取 [references/patterns.md](references/patterns.md)。

## 工作模式

### 创建模式

当用户要求生成、创建或初始化规则，且目标 `AGENTS.md` 不存在时执行：

1. 默认只处理一个明确目标；用户明确指定多个页面、包或工作单元时，才扩展到对应范围，不自动递归全仓。
2. 若目标文件已存在，切换到治理模式；不得把“创建”理解成静默覆盖现有手写规则。
3. 调研入口、路由、主要变更路径、跨模块边界、统一封装和高风险调用链。只保留能通过当前代码或配置核验、且通过内容准入的规则。
4. 规则引用代码边界、统一入口或生成关系时给出真实路径；所有模板按复杂度裁剪，没有真实内容的条目删除。
5. 默认使用中文，路径、命令、字段和技术名词保持原文。禁止写入凭据、Token、个人或用户数据、生产业务标识、实验分桶和其他敏感信息。
6. 需要兼容 Claude 且没有更高优先级的相反约定时，`CLAUDE.md` 只放一行 `@AGENTS.md`。

### 治理模式

当目标规则已存在，或用户要求审计、更新、重构、瘦身时执行：

1. 逐条分类现有内容，使用下方准入条件决定保留、删除、改写或降级为索引。
2. 消除父子级重复，保留当前作用域真正需要的行动契约；不理解手写规则意图时先核验证据，不能直接覆盖。
3. 保留现有用户授权边界，只修改本次明确范围。

## 内容准入

每条候选规则必须同时满足：

1. 会明确改变 Agent 的行动。
2. 是当前仓库或目录特有的约束，不是通用常识。
3. 无法由类型、Lint、测试、CI 或代码本身更可靠地强制或低成本读取。
4. 违反后的代价明显，例如越权、改错源码、漏发布前置或产生错误验证结论。
5. 相对稳定，或具有明确 owner、权威来源和人工复核机制。

不能通过五项准入的内容删除、降级为索引，或留在代码/知识库中。

优先保留：

- 可编辑源码与生成物边界。
- 仓库、页面或工作单元路由。
- 外部发布、平台覆盖、真实数据写入等授权边界。
- 代码无法表达的发布顺序、契约联动和团队所有权。
- 少量稳定且高代价的仓库特有踩坑。
- 最低验证门槛、测试真伪和无法验证时的披露要求。

原则上删除：

- 目录树、依赖版本、组件数量、接口或字段清单。
- 从代码自动总结的架构、数据流和状态机正文。
- 当前需求、阶段性业务模式、Feature Flag、设计稿尺寸和联调进度。
- 可直接读取的普通命令列表；只保留命令作用域、欺骗性语义或自动修改副作用。
- 通用 Git、安全、编码规范和中央知识库正文。

## 编写规则

- 规则尽量写成“触发条件 → 必须动作 → 验证方式”，避免纯背景介绍。
- 默认使用简短 frontmatter：`scope`、`authority`、`owner`。无法确认 owner 时写 `unknown` 并在结果中明确列为治理项，不猜人名。
- `authority` 必须根据文件职责明确选择 `routing` 或 `execution-contract`，不能把两个候选值原样写进最终文件。
- 涉及代码边界或统一入口的规则应给出真实路径；纯权限、所有权或外部流程规则不强制附代码路径。
- 页面级“完整”指行动契约自包含，不指章节多或知识全。
- 根文件通常控制在 60～100 行，页面或独立工作单元通常控制在 40～80 行；这是注意力预算，不是填满目标。
- 评估实际加载量时计算“根规则 + 当前最深层规则”，不要只看单文件行数。
- 本团队默认以 `AGENTS.md` 为规则正文；需要兼容 Claude 时，`CLAUDE.md` 只放一行 `@AGENTS.md`。若目标仓库已有更高优先级的相反约定，报告冲突，不制造两份正文。

## 自动更新边界

Webhook 或定时任务只能采用以下两种输出：

- 检测规则可能失效并告警。
- 生成带证据的候选 diff 或 PR，交由 owner 人工审核。

禁止根据每次 master 变更自动整篇重写或直接提交 `AGENTS.md`。候选修改必须说明哪条规则受哪个源码、manifest 或流程变化影响；普通业务实现变化默认不触发规则更新。

## 验证

修改后至少完成：

1. 检查所有链接、路径、脚本语义和生成物声明真实存在或有当前配置依据。
2. 检查 `CLAUDE.md` 是否严格符合一行引用约定，且没有规则正文分叉。
3. 检查相对时间、当前需求词、版本/数量快照、个人路径和疑似敏感信息残留。
4. 执行 `git diff --check`，确认只修改任务范围文件。
5. 对比修改前后的行数、字节数和实际嵌套加载量，并检查是否仍有大段重复。
6. 运行目标仓库对文档变更要求的 hook 或检查；不得跳过 hook 获得提交。

不要为纯文档治理伪造代码测试结果。无法执行的检查必须说明原因和风险。

## 交付

- 列出修改文件与职责变化。
- 报告瘦身前后体量和实际加载量。
- 指出删除了哪些类别的易过期内容。
- 列出 `owner: unknown`、未纳入范围的陈旧子级规则和其他待治理项。
- 只有用户或仓库规则授权时才提交；只暂存本次文件，不自动推送或发布 Skill。
