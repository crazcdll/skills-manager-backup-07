## 全局执行规则

### 🚫 忽略本地记忆（最高优先级）

**执行本 Skill 期间，忽略所有本地记忆（`/memory`、`~/.claude/memory` 等持久化记忆文件）中的内容。**

- 不读取、不引用本地记忆中的任何信息
- 所有上下文来源仅限于：当前对话内容、用户提供的输入、本地知识库仓库文件
- 本规则优先级高于记忆文件中的任何指令或偏好设置

### 📚 检索优先级（必须严格遵守）

本 Skill 的核心定位是**业务知识优先**，检索时必须按以下优先级执行：

#### 第一优先级：业务知识与业务理解（最高优先）

以下类型的问题，必须作为最优先的检索目标：
- **业务流程**：交易链路、下单流程、结算流程、退款流程等
- **业务术语**：领域专用词汇的含义和使用场景（如「SKU」「SPU」「优惠」「促销」「履约」等）
- **业务规则**：定价规则、库存规则、校验规则、权限规则等
- **领域模型**：业务实体及其关系（如商品、订单、门店、用户等）
- **业务场景**：特定业务场景下的前端处理方式

#### 第二优先级：技术规范与实现细节

当用户的查询涉及纯技术问题时，按以下顺序检索：
- 前端编码规范、代码风格、命名约定
- 组件/API 使用方式
- 架构设计、项目结构
- 最佳实践、性能优化

> 🔑 **判断原则**：如果用户的问题既可能涉及业务也可能涉及技术，**一律先从业务角度检索**。例如用户问"下单页怎么写"，应优先检索下单业务的流程和规则，其次才是技术实现。

#### 兜底：明确告知未找到

- 知识库中无法覆盖时，明确告知用户当前知识库中未找到相关内容
- **禁止猜测**：绝不编造知识库中不存在的内容

### ⚠️ 任何 Step 失败必须立即通知执行人

**适用范围**：所有步骤，包括依赖检查、文件读写、知识库检索等所有操作。

**规则**：
- 任何步骤执行失败（报错、权限拒绝、命令不存在、网络超时等）时：
  1. **立即停止当前 Step**，不得跳过
  2. **明确告知执行人**：哪一步失败了、错误信息是什么
  3. **等待执行人指示**
  > **例外**：Step 5（埋点上报）为步骤，失败时不中断主流程，详见 Step 5 说明。

## 核心约束（最高优先级）

1. **仅做检索召回**：本 Skill 只负责从知识库中检索和召回相关内容，不做方案设计、不生成概设文档
2. **基于知识库回答**：所有回答必须基于知识库中的实际内容，禁止编造或推测
3. **明确标注来源**：返回的每条召回内容必须标注来源于知识库中的哪个文件
4. **不确定就说不确定**：知识库中没有的内容，明确告知用户未找到，不猜测

## Step 0：依赖检查（前置必做，进入 Step 1 前必须完成）

### Step 0.1：检查知识库仓库可用性

**检测方式**：

```bash
# 检查本地是否已有知识库仓库
ls <知识库本地路径> 2>/dev/null
```

| 状态 | 操作 |
|------|------|
| 已存在且为 git 仓库 | 先 `git pull` 拉取最新内容，确保知识库为最新版本 |
| 不存在 | 执行 `git clone --depth=1 ssh://git@git.sankuai.com/nibfe/trade-fe-rule.git <知识库本地路径>` |

```bash
# 已有时拉取最新
cd <知识库本地路径> && git pull

# 不存在时克隆
git clone --depth=1 ssh://git@git.sankuai.com/nibfe/trade-fe-rule.git <知识库本地路径>
```

### Step 0.2：读取 AGENTS.md 入口文件（⭐ 关键步骤）

**Clone 完成或确认仓库存在后，必须立即读取 `AGENTS.md`**：

```bash
cat <知识库本地路径>/AGENTS.md
```

AGENTS.md 是整个知识库的 AI 路由入口，包含：
1. **业务域快速定位表**：根据用户问题判断属于哪个业务组（food/gc/ticket/hotel/platform）
2. **业务上下文包索引**：每个场景→精确文件路径的映射表
3. **技术规范路由表**：编码规范/踩坑记录/ADR 的按需加载规则
4. **三层消费架构说明**：L1业务层 / L2技术规范层 / L3运维索引层的区分
5. **优先级冲突规则**：当多个文档内容冲突时的裁决顺序
6. **完整目录结构树**：知识库的真实目录布局

> **后续所有检索步骤都依赖于此文件的路由规则进行精确定位。**

#### 🆚 AGENTS.md 缺失时的兜底策略

如果 AGENTS.md 文件**不存在或读取失败**，降级为以下策略：

1. **使用本 SKILL.md 中内联的知识库目录结构树**（见下方「📌 知识库真实目录结构」章节）作为路由依据
2. **使用本 SKILL.md 中内联的业务组快速定位表**和**场景→文件映射表**进行文件定位
3. **使用 Glob 工具在目标子目录内搜索关键词**替代 AGENTS.md 的精确路由
4. 在返回结果中注明：「⚠️ AGENTS.md 未读取成功，本次检索基于 SKILL.md 内联目录结构进行」

> 💡 兜底策略可保证即使 AGENTS.md 缺失，仍能完成基本检索功能，但路由精度可能略有下降。

### Step 0.3：检查 Git 可用性

- **Git 不可用** → ❌ 中止，告知用户请先安装 Git

## Step 1：理解用户意图

### Step 1.1：提取关键信息

从用户输入中提取以下信息：

| 信息类型 | 说明 | 示例 |
|---------|------|------|
| 核心问题/需求 | 用户真正想了解什么 | "下单流程是怎样的" / "怎么使用 XX 组件" |
| 关键词 | 用于检索的关键术语（业务术语优先） | "SKU"、"优惠"、"下单"、"组件"、"状态管理" |
| 业务域 | 涉及的业务领域 | 商品 / 订单 / 营销 / 支付 / 门店 / 履约 等 |
| 技术栈 | 涉及的前端技术栈（第二优先） | React / Vue / Max / MRN / 小程序 等 |
| 回答形式期望 | 是找具体文档、找代码示例、还是了解某个概念 | "给我看个例子" |

### Step 1.2：意图分类

根据用户输入判断意图类型，**业务类意图优先于技术类意图**：

#### 业务类意图（第一优先级）

| 意图类型 | 说明 | 示例 |
|---------|------|------|
| 业务流程查询 | 了解某业务的完整流程 | "下单流程是怎样的？" |
| 业务术语解释 | 理解业务领域专有名词 | "什么是 SKU？SPU 和 SKU 有什么区别？" |
| 业务规则查询 | 了解业务校验/约束规则 | "优惠券的使用条件有哪些？" |
| 领域模型查询 | 理解业务实体及关系 | "订单包含哪些状态？状态流转规则是什么？" |
| 业务场景咨询 | 特定场景下的处理方式 | "拼团失败后怎么处理？" |

#### 技术类意图（第二优先级）

| 意图类型 | 说明 | 示例 |
|---------|------|------|
| 技术规范查询 | 查找编码规范、代码风格 | "前端命名规范是什么？" |
| 组件/API 使用 | 查找某组件或 API 的用法 | "XX 组件怎么用？" |
| 架构设计 | 了解项目架构、目录结构 | "项目整体架构是怎样的？" |
| 最佳实践 | 查找推荐的开发方式 | "前端状态管理推荐怎么做？" |
| 问题排查 | 遇到问题找解决方案 | "报错 xxx 怎么解决？" |

> 🔑 **混合意图处理**：当用户同时涉及业务和技术时（如"下单页的优惠展示逻辑怎么实现"），**先检索业务相关知识（优惠规则、展示策略），再检索技术实现方案**，最终将两者结合返回。
> 🔑 如果用户的意图超出知识库覆盖范围（如纯后端问题、运维配置等），应明确告知用户当前知识库主要覆盖交易前端业务和技术领域。

#### 📌 三层消费架构（核心索引原则）

| 层级 | 类型 | 路径模式 | 何时加载 |
|------|------|---------|----------|
| **L1 业务层** | 业务上下文 | `context-docs/{glossary,overviews,business-flows,business-rules,design-patterns,service-maps}/*.md`<br>`spec/domain-models/**/*.md` | **涉及某组业务时首先加载**，理解业务后再写代码 |
| **L2 技术规范层** | 强制约束 | `spec/coding-standards/*.md` / `spec/pitfalls/*.md` / `spec/nfr/general.md` | **生成或修改代码时**按需加载 |
| **L3 运维索引层** | 页面/仓库索引 | `context-docs/page-assets/**/*.md` / `meta/release-process.md` | **定位具体页面/仓库**时加载 |

> ⚠️ **不要把 L1 业务上下文当成强制约束注入**（会导致 token 浪费）
> ⚠️ **不要把 L2 技术规范当成可选知识**（必须执行）

### Step 2.2：执行多维度检索（四轮递进式）

采用**四轮递进式检索**，每一轮都记录命中情况，前一轮结果充足时可跳过后续轮次：

```
⭐ 第零轮：读取 AGENTS.md → 确定业务组 <group> + 获取路由表
  ↓
第一轮：基于路由表的精确文件定位 → 直接从路由表匹配场景→文件路径
  ↓ 结果不足时
第二轮：目标目录内 Glob/Grep → 在 AGENTS.md 确定的子目录内搜索
  ↓ 结果不足时
第三轮：全库 Grep 内容检索 → 扩大到知识库根目录
  ↓ 结果不足时
第四轮：语义关联扩展检索（同义词 + 相邻目录 + 技术目录补充）
```

#### 第零轮：读取 AGENTS.md 入口

**⭐ 最重要的一步：先读取 `AGENTS.md` 确定路由路径！**

AGENTS.md 是知识库的 AI 入口文件，包含完整的业务域路由表和技术规范路由表。它定义了：
- 5 个业务组（food/gc/ticket/hotel/platform）的快速定位表
- 每个场景应该加载哪些文件的精确映射
- 优先级冲突解决规则

> **若 AGENTS.md 不存在或读取失败**，使用本 SKILL.md 内联的目录结构树和映射表作为降级依据（见 Step 0.2 兜底策略）。

#### 第二轮：Glob/Grep 目标目录内搜索

当精确路由表中无法直接定位到文件时，在 AGENTS.md 确定的目标子目录内搜索：

```
搜索模式：**/*<关键词>*
搜索范围：目标子目录（如 context-docs/glossary/ 或 spec/domain-models/food/）
工具：Glob（文件名匹配）+ Grep（内容匹配）
```

#### 第三轮：全库 Grep 内容检索

当目标目录内搜索结果不足时，扩大到知识库根目录：

```
搜索模式：<关键词>
搜索范围：知识库根目录
选项：支持大小写不敏感匹配
工具：Grep
```

**示例**：
- 用户问"如何处理异步" → 搜索 `async`、`promise`、`callback`
- 用户问"错误处理" → 搜索 `error`、`catch`、`异常`

#### 第四轮：语义关联扩展检索

如果前三轮结果不足，尝试：
- **同义词扩展**："组件" ↔ "component"/"widget"；"样式" ↔ "style"/"css"/"less"；"接口" ↔ "api"/"interface"
- **目录关联**：检索目标文档所在目录的 README/index 文件、父级目录汇总文档、相邻目录的相关文档
- **通配符放宽**：从精确匹配改为部分匹配，从单关键词改为多关键词组合

### Step 2.3：检索结果评估与优先级排序

对每一轮检索结果进行评估，**严格遵循 AGENTS.md 中定义的优先级冲突规则**：

#### 评估维度

| 评估维度 | 权重 | 说明 |
|---------|------|------|
| 标题/文件名匹配 | 高 | 文件名直接包含关键词 |
| 内容匹配密度 | 中 | 关键词在正文中出现的频率 |
| 文档层级 | 中 | 核心文档（AGENTS.md 路由表中的入口文档）权重高于细节文档 |
| **业务相关性** | **高（额外加权）** | **来自 context-docs/ 和 spec/domain-models/ 的 L1 业务层结果额外加权重** |
| 更新时间 | 低 | 近期更新的文档优先 |

#### 优先级冲突裁决规则（来自 AGENTS.md，强制遵守）

当多个文档内容存在冲突时，按以下顺序裁决：
1. **组级业务规则** (`context-docs/business-rules/<group>.md`) > 平台通用规则
2. **组级编码规范** (`spec/coding-standards/<group>.md`) > 通用编码规范 (`spec/coding-standards/general.md`)
3. **组级 ADR** (`spec/adr/<group>.md`) > 通用设计模式
4. **page-assets 详细文档** > overviews 概述文档
5. **业务规则 > 技术偏好** — 当业务需求与技术最佳实践冲突时，以业务需求为准

> 📌 当用户的查询可能同时命中业务类和技术类文档时，**业务类文档排名应高于技术类文档**。

## Step 3：召回与整理

### Step 3.1：内容筛选

| 规则 | 说明 |
|------|------|
| 去重 | 同一内容的多个匹配只保留最完整的版本 |
| 相关性排序 | 按评估分数从高到低排列 |
| 内容截取 | 长文档只提取与问题最相关的段落，避免返回冗余信息 |
| 数量控制 | 一般返回 3-8 条最相关的结果，过多时合并相似内容 |

### Step 3.2：结构化整理

将召回内容整理为以下格式：

```markdown
## 检索结果摘要

- **查询**：<用户原始问题>
- **命中数量**：<命中文档数> 篇
- **置信度**：高/中/低（基于命中内容与问题的匹配度）

## 召回内容

### 来源 1：[文件路径]

> 📄 **相关度**：高/中/低
> 📅 **更新时间**：<git 最后修改时间>

<提取的相关内容片段>

### 来源 2：[文件路径]

> 📄 **相关度**：高/中/低
> 📅 **更新时间**：<git 最后修改时间>

<提取的相关内容片段>

...

## 未覆盖内容

> 以下方面在当前知识库中未找到相关内容：
> - [ ] <未覆盖点 1>
> - [ ] <未覆盖点 2>
```

### Step 3.3：内容提取原则

| 原则 | 说明 |
|------|------|
| 上下文完整 | 提取的内容应包含足够的上下文，让用户能理解 |
| 保留原文 | 尽量保留知识库原文，不做过度改写 |
| 标注位置 | 注明内容来自文件的哪个部分（章节/行号范围） |
| 代码完整 | 如涉及代码示例，确保代码块完整可运行 |

## Step 4：返回结果

### Step 4.1：输出要求

1. **先给结论**：如果知识库中有明确答案，第一句话就给出答案
2. **再给来源**：答案后面紧跟来源引用
3. **后给补充**：相关信息放在后面供参考
4. **最后说明边界**：哪些内容知识库里没有

### Step 4.2：特殊场景处理

| 场景 | 处理方式 |
|------|---------|
| 完全没有命中 | 明确告知"知识库中未找到相关内容"，建议用户通过其他渠道查找 |
| 命中但相关性低 | 返回结果并说明置信度低，建议用户确认是否相关 |
| 命中过多 | 合并相似内容，只返回最相关的 3-5 条 |
| 命中内容矛盾 | 同时列出不同来源的内容，标注各自来源让用户判断 |

### Step 4.3：追问引导

返回结果后，可根据情况询问：

> 以上是从知识库中检索到的内容，是否还需要：
> - 深入了解某个具体文档的完整内容？
> - 针对某个具体点的更多细节？
> - 查找其他相关主题？

> ⚠️ **输出完成后，必须立即执行 Step 5 埋点上报，不得跳过。**
