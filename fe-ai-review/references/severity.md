# 定级与证据判断

主审在分析候选问题和组织最终发现项时读取本文。先确认问题是否成立，再按有证据支持的业务影响定级；规则命中、强制措辞和专项扫描给出的候选级别不能替代最终判断。

## 判断维度

| 维度 | 核对内容 |
|---|---|
| 置信度 | 对问题成立、触发路径和所述后果的证据是否充分；不是模型自报的分数 |
| 触发条件与频率 | 正常操作必现、常见条件触发、偶发，还是极端条件触发 |
| 影响范围 | 单次操作、明确的用户群体（机型、App、系统版本等），还是全部用户 |
| 业务重要度 | 支付、下单、价格等关键场景，还是辅助功能 |
| 问题后果 | 操作受阻、错误交易、数据或安全损害、局部展示问题；能否恢复、绕过或由有效兜底消除 |

这些维度用于综合判断，不做加权打分或机械逐项比较。全量可见的轻微样式问题不会因此升级；严重资金、数据或安全损害也不因人数少、触发频率低而自动降级。

## 严重度

| 级别 | 口径 |
|---|---|
| P0 | 证据充分：正常或常见条件下，全部用户或明确用户群体的关键业务持续不可用且无有效兜底；或造成严重资金、数据、安全损害，需要立即阻止发布 |
| P1 | 证据充分：重要功能明显受损，需要优先修复，但触发条件、影响范围、实际损害或可恢复性使后果未达到 P0 |
| P2 | 已确认的局部功能或展示问题，影响有限，核心任务仍可完成 |
| P3 | 轻微体验问题或有具体依据的维护性改进，不造成显著业务损害；仍遵守 Skill 的默认不报范围 |

P0/P1 的问题成立和定级依据均应达到较高置信：能指出具体代码、实际可达的触发路径及其业务后果，并核对已有保护。交给 `ai-quality-cr-agent` 时，至少能分别填出 `reach_analysis`（如何触达）、`online_scenario`（什么线上条件触发）和 `impact_scope`（影响哪些用户或业务）；不能填出实质内容时，不保留为 P0/P1。高置信的小问题仍是 P2/P3；低置信的严重后果不能通过附注“待确认”继续作为 P0/P1 发布。

“重要场景 + 展示异常”不直接构成 P0。例如价格文字错位但仍可准确阅读，属于局部体验问题；展示价格错误需按对交易的实际影响定级；实际错扣款则需判断资金损害。白屏也需区分关键交易入口持续不可用和辅助页面可恢复的异常。

## 高级别候选的补证步骤

1. 明确异常条件：什么输入、状态、操作顺序、机型或版本会触发。例如上游返回空列表，而不是笼统的“特殊情况”。
2. 追溯条件来源：读取相关调用方、接口契约和输入处理，核对上下游是否可能产生该条件。类型声明是线索，不自动证明运行时输入受到限制。
3. 核对完整路径：条件能否到达问题点，校验、分支、异常处理或兜底是否实际消除了所指后果。有 catch 不等于业务损害已消除。
4. 确认业务影响：哪些用户的什么任务受损，能否恢复或绕过。区分代码现象与业务后果，只保留有依据的影响描述。
5. 按下表处置候选问题。

证据足以确认或排除时停止补读。关键事实依赖无法获取的配置、接口保证或业务约定时，明确缺口，不围绕同一份证据反复推演。

| 补证结果 | 处理 |
|---|---|
| 问题及所述后果均得到支持 | 按实际影响定级 |
| 问题成立，但只证实较小影响 | 缩小问题描述，按已证实后果定级，删除无依据的严重后果推断 |
| 关键事实仍待确认，且满足下述准入条件 | 进入待确认问题（Open Questions） |
| 只有理论可能、假设链过长或已被反证推翻 | 不输出 |

不能把同一个低置信 P0 猜测改贴 P2 标签。比如已确认价格展示错误，但没有证据证明错扣款，应报告展示问题的真实影响，而非报告“P2：可能错扣款”。

## 待确认问题（Open Questions / confirm）

与 `ai-quality-cr-agent` 的“待确认问题”对应：已有可定位的代码或契约线索，但问题是否成立或实际影响仍依赖关键事实。仅保留核实结果会影响修复、测试或发布判断的候选；泛泛提醒、已排除的问题不收录。

每条保留标题、真实文件与行号、已知事实，并按以下内容组织，便于上层直接转换：

| 报告内容 | `ai-quality-cr-agent` 字段 | 要求 |
|---|---|---|
| 问题描述 | `description` | 已观察到的代码行为或契约线索 |
| 不确定原因 | `confirm_reason` | 缺少哪个事实，为什么当前无法确认 |
| 可能的风险 | `possible_risk` | 若条件成立，会发生什么后果；明确条件，不补写影响规模 |
| 确认建议 | `confirm_suggestion` | 核对哪个契约、配置或调用方，或如何验证 |

例如，定位到列表读取语句后：

- 问题描述：提交路径直接读取上游列表的首项，未找到空列表处理。
- 不确定原因：未找到接口保证列表非空的依据。
- 可能的风险：若上游允许返回空列表，该路径会触发异常并中断提交。
- 确认建议：核对接口的空结果契约及调用方处理。

对外使用“待确认问题”，兼容 `Open Questions` 名称；委托给 `ai-quality-cr-agent` 时由上层按交接协议转换为 `severity=confirm`，补齐通用必填字段。`confirm` 表示待确认，不是严重度，也不同于复审 verdict `CONFIRM`（确认原问题）。不得伪造定位信息或用候选 P0 标签代替描述。

待确认问题单独计数，不计入 P0–P3 缺陷数，也不因其存在自动推导阻塞或需修复。人工确认条件成立后仍需按实际影响定级。即使确定性缺陷为零，摘要也要明确待核实条件，不能把“未发现已确认缺陷”说成“风险已排除”。

普通覆盖缺口记录在覆盖自评，不作为待确认问题上报。
