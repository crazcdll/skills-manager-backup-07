# 失败设计规范

## 一、说明

本规范定义了服务间调用的失败设计标准，涵盖超时、重试、熔断、降级和限流五个核心领域。失败设计是高可用体系的基石——任何外部依赖都可能失败，系统建议在依赖失败时仍能提供核心功能或优雅降级。

本规范的关注维度是"如何在依赖失败时不崩溃"，与通用编码规范中的异常处理（关注"如何正确使用异常机制"）和并发处理（关注"如何正确编写并发代码"）形成互补。

## 二、规则内容

### HA-F001 [推荐] 超时建议显式设置

所有 RPC 调用（OCTO/MTthrift）、HTTP 请求、数据库操作、缓存操作建议显式设置超时时间，不建议依赖框架默认值。

**说明**：
- OCTO/MTthrift 建议在 XML 或注解中显式配置 `timeout`
- HTTP 请求建议同时设置 `connectTimeout` 和 `socketTimeout`
- 超时值建议通过 Lion 配置中心管理，支持动态调整
- 上下游超时协调原则：调用方超时 > 被调方处理时间，网关超时（Oceanus）> 后端服务超时（Shepherd）

### HA-F002 [推荐] 重试建议满足前提条件

重试建议同时满足：幂等性保证、指数退避+随机抖动、最大重试次数限制（建议 ≤3 次）。

**说明**：
- 写操作重试前建议确认幂等性（通过幂等 Key 或数据库唯一约束）
- 退避公式：`delay = min(baseDelay * 2^attempt + random(0, baseDelay), maxDelay)`
- 不建议固定间隔重试（会导致重试风暴）
- 不建议无限重试

### HA-F003 [推荐] 熔断建议使用平台能力

熔断建议使用 Rhino 平台，不建议自行实现。熔断触发条件至少满足三条件之一：错误率超阈值、超时率超阈值、并发数超阈值。

**说明**：
- 使用 `@RhinoCommand` 注解或 Rhino SDK 接入
- 建议配置 fallback 方法，fallback 中不建议再调用可能失败的外部依赖
- 业务异常（如参数校验失败）应加入白名单，不计入熔断窗口
- 半开状态的探测请求比例建议 ≤10%

### HA-F004 [推荐] 降级建议使用独立路径

降级开关的标准化管理（boolean 类型、默认关闭、Lion 配置、命名、嵌套层级、清理周期）遵循 `HA-11` HA-CF002；本条聚焦降级专属约束。降级路径建议独立于正常路径，不建议复用正常路径的异常分支。

**说明**：
- 降级触发时建议打印 WARN 日志并发送告警
- 降级返回值建议有业务含义（如默认商品列表、兜底推荐），不建议返回空值或异常
- 核心链路和非核心链路的降级策略建议分离
- **流量联动**：降级触发条件应与限流配合——当限流触发率持续上升时，应主动降级非核心功能；降级建议支持 ≤5s 生效（Lion 推送延迟）

### HA-F005 [推荐] 限流建议配置

所有对外提供的核心接口建议配置限流，使用 Rhino 平台限流。

**说明**：
- 限流阈值基于压测结果和日常峰值流量设定，建议为日常峰值的 1.5~2 倍
- 建议配置 Token Server 模式的兜底限流（集群限流）
- 单机限流和集群限流建议同时配置
- 限流触发时返回 HTTP 429 或自定义错误码，不建议返回 500

##### good case:

```java
// Rhino 限流注解
@RhinoRateLimit(
    resourceName = "orderService.createOrder",
    qps = 5000,
    fallbackMethod = "createOrderLimited"
)
public OrderResult createOrder(OrderRequest request) {
    return doCreateOrder(request);
}

// 限级 fallback — 返回有意义的错误
public OrderResult createOrderLimited(OrderRequest request) {
    log.warn("createOrder rate limited, userId={}", request.getUserId());
    return OrderResult.rateLimited("系统繁忙，请稍后再试");
}
```

#### bad case:

```java
// 核心接口不配置限流就上线 — 可能被突发流量打垮
public OrderResult createOrder(OrderRequest request) {
    return doCreateOrder(request);
}
```

## 三、示例

以下示例仅用于说明规则边界与意图，不代表唯一实现方式；实际生成或审查代码时，应优先复用项目现有框架、工具类、SDK 与命名，并以是否满足规则约束为判断标准。

### HA-F001 超时显式设置示例

#### good case:

```java
// OCTO/MTthrift 显式配置超时
@ThriftClient(timeout = 3000, connTimeout = 1000)
private UserService userService;

// HTTP 请求显式设置超时
RequestConfig config = RequestConfig.custom()
        .setConnectTimeout(1000)
        .setSocketTimeout(3000)
        .build();

// Lion 动态超时配置
@LionValue("${service.user.timeout:3000}")
private volatile int userServiceTimeout;
```

#### bad case:

```java
// 依赖框架默认超时（可能是 30s 甚至无限）
@ThriftClient
private UserService userService;

// HTTP 请求未设置超时
HttpClient client = HttpClients.createDefault();
client.execute(request);
```

### HA-F002 重试设计示例

#### good case:

```java
// 指数退避 + 随机抖动 + 最大次数限制
public <T> T retryWithBackoff(Supplier<T> action, int maxRetries) {
    for (int i = 0; i < maxRetries; i++) {
        try {
            return action.get();
        } catch (RetryableException e) {
            if (i == maxRetries - 1) throw e;
            long delay = Math.min(100L * (1L << i) + ThreadLocalRandom.current().nextLong(100), 5000);
            Thread.sleep(delay);
        }
    }
}
```

#### bad case:

```java
// 固定间隔重试 — 会导致重试风暴
for (int i = 0; i < 10; i++) {
    try {
        return callRemoteService();
    } catch (Exception e) {
        Thread.sleep(1000); // 固定 1s
    }
}

// 写操作重试但未保证幂等
public void createOrder(OrderRequest request) {
    retryWithBackoff(() -> orderService.create(request), 3); // 可能创建重复订单
}
```

### HA-F003 熔断设计示例

#### good case:

```java
@RhinoCommand(
    fallbackMethod = "getUserFallback",
    commandProperties = {
        @RhinoProperty(name = "circuitBreaker.errorThresholdPercentage", value = "50"),
        @RhinoProperty(name = "circuitBreaker.requestVolumeThreshold", value = "20"),
        @RhinoProperty(name = "execution.isolation.thread.timeoutInMilliseconds", value = "3000")
    }
)
public UserInfo getUser(Long userId) {
    return userService.getById(userId);
}

// fallback 不依赖外部服务
public UserInfo getUserFallback(Long userId, Throwable t) {
    log.warn("getUser fallback triggered, userId={}", userId, t);
    return UserInfo.defaultInstance();
}
```

#### bad case:

```java
// 无熔断保护的外部调用
public UserInfo getUser(Long userId) {
    return userService.getById(userId); // 下游故障时会拖垮当前服务
}

// fallback 中再调用外部服务
public UserInfo getUserFallback(Long userId, Throwable t) {
    return backupUserService.getById(userId); // 可能继续失败
}
```

### HA-F004 降级设计示例

#### good case:

```java
// Lion 开关控制降级
@LionValue("${recommend.degrade.enabled:false}")
private volatile boolean recommendDegradeEnabled;

public List<Product> getRecommendations(Long userId) {
    if (recommendDegradeEnabled) {
        log.warn("recommend service degraded, userId={}", userId);
        Cat.logEvent("Degrade", "recommend");
        return getDefaultRecommendations(); // 独立的降级路径
    }
    return recommendService.getForUser(userId);
}
```

#### bad case:

```java
// 降级返回空值
public List<Product> getRecommendations(Long userId) {
    try {
        return recommendService.getForUser(userId);
    } catch (Exception e) {
        return Collections.emptyList(); // 无业务含义，前端可能展示空白
    }
}
```

## 四、规范执行要点

- ✗ 不建议依赖框架默认超时
- ✗ 不建议固定间隔重试
- ✗ 不建议写操作在未保证幂等时重试
- ✗ 不建议自行实现熔断（建议使用 Rhino）
- ✗ 不建议 fallback 中再调用可能失败的外部依赖
- ✗ 不建议降级返回空值或异常（建议有业务含义）
- ✗ 不建议核心接口不配置限流就上线
